## 1. 原始问题与讨论范围

原第 31 项希望拓展 SSC 社会关系，将与主从体系有关的关系与原版关系组合，使多重联系显示得更清楚，同时尽可能保留配偶、恋人、亲属等基础关系的识别与必要玩法行为。

讨论首先倾向于保留基础记录、合成展示，随后发现“只查询社会关系”涉及现有 SSC 记录的方向缺失、覆盖范围和奖励效果。由此延伸到有向基础关系、直接改造旧关系、特化动态关系和三层架构等可能性。这些方案均未实装；当前也不继续指定其中哪条路线。

维护者在讨论中提出的范围偏好包括：

- 希望合成器尽可能只读社会关系，甚至将其作为唯一关系查询接口。这里指关系数据，不是解析社交页面上的文字，也不要求先打开页面。
- 调教员暂不考虑，因为目前没有可通过社会关系独立查询的对应关系。
- 不另外引入“仪式羁绊／已获奖励”等组合状态；已经存在的 SSC 社会关系可作为输入，不要求合成器了解它的获得过程。
- 同主关系可以研究由社会关系推导，也可以考虑专门的社会关系；没有决定新增。

上述偏好是讨论背景，不是冻结的未来需求。最新决定是暂缓并仅作资料留存。

## 3. 讨论过的候选方案

| 候选 | 讨论中的收益 | 限制与未决问题 |
| --- | --- | --- |
| 保留基础记录，只合成展示 | 能保留原版关系身份及既有建立／解除流程；复合称谓不必存档 | 现有 SSC 记录没有方向，也未覆盖全部绑定；如何获得特化等信息仍需定义。 |
| 另加有向基础关系 | 曾提出从属侧保存主人记录，反向以 implied 关系推导；能补足方向信息 | 增加新的关系定义与维护职责，需决定是否覆盖全部绑定、如何与原奖励关系共存。详细旧草案见文末，仅作比较。 |
| 直接改造现有 SSC 关系 | 保留原 defName，改成一个方向的直接记录，另加反向推导 Def，可减少并行基础记录 | 必须迁移旧档、修改双向直接查询、维护原有效果；主人一侧可能不再以原 Def 被第三方识别。 |
| 保留统一羁绊，动态展示特化称谓 | 稳定记录可对应随特化变化的称谓，不必逐次删除重建旧关系 | 动态名称与主从方向是不同信息；如果特化仅存于组件／Hediff，纯社会关系查询仍无法直接取得。 |
| 三层结构 | 将 SSC 内部信息解释和最外层通用组合分开 | 对外 Def 的性质、公开查询入口、效果归属、缓存与生命周期均未决定。详见下一节。 |
| 用复合关系替换原版基础记录 | 曾作为比较对象分析 | 精确 Def 比较、直接列表枚举、计数与删除流程可能失效，无法凭映射或 XML 继承承诺全面兼容；没有采用决定。 |

“同主”不能仅凭当前无向记录的共同邻居确定：`甲—乙—丙` 既可能表示甲、丙共同属于乙，也可能是甲拥有乙、乙拥有丙；原记录覆盖不完整还可能导致漏判。

直接改造旧 Def 时，保留原取得条件只会让原有关系拥有方向，不会覆盖全部绑定。若扩大到所有绑定并照搬 +100 和同床最高档条件，则改变奖励覆盖范围；若扩大覆盖又保留奖励差异，则需另行保存或表达该差异。两者都没有在本次讨论中确定。

## 4. 最后提出的三层结构

维护者提出以下结构；该结构是讨论提案，不是已选定的重置或开发架构：

```text
底层：现有无方向性 Def，以及锁链、特化等其他 SSC 信息
                         ↓
中层：SSC 内部社会关系处理，依据底层信息合成／选定社会关系 Def
                         ↓
外层：仅读取社会关系，与原版及其他模组关系组合，生成复合展示
```

这将“只查询社会关系”的约束放在最外层。中间层可以解释方向、特化与 SSC 资格，外层不必了解这些状态保存在哪个组件。它也允许先保留现有无方向 Def，而不是先决定把它改成归属关系。

讨论中的示例是：中间层可根据方向与特化，分别向两种观察视角提供“主人”或“宠物”等关系，外层再将其与配偶等关系组合。所有示例名称只是说明职责，不是新增 Def 清单或正式文案。

尚未决定的问题包括：

- 中间层输出的是原生可查询的 `PawnRelationDef`、仅供统一接口使用的结果，还是保存的直接关系；是否采用 implied Worker 也未确定。
- 中间层选定关系要求旧 Def 存在，还是只需有效绑定；需要表达当前身份、既有羁绊还是两者。
- 哪层承担原有效果及可能的特化效果；底层和中层同时参与关系枚举时如何避免重复。
- 对外关系是每方向一个、允许多个并存，还是采用其他映射；特化冲突、缺少方向与默认结果如何处理。
- “社会关系可查询”具体覆盖原生查询、直接列表、SSC 专用入口和哪些第三方系统。
- 若实时派生，如何避免 Worker 递归并处理原生查询前置过滤、角色候选发现和刷新；若保存结果，如何处理同步、存档与人格流转。

曾分析可预先声明有限 Def，再按状态选定，避免运行时反复创建 Def 或修改共享 Def 的名称。此思路仅是实现可能性，不视为推荐结论或后续实施要求。

## 5. 关于原作者意图的假设

维护者提出：原作者使用无方向性 Def，可能是为了支持基于特化的动态社会关系。

该假设在设计上可以成立，但现有证据不足以确认动机。本仓库最早可追溯提交 `94cd803`（2026-08-14）已采用相同的双向定义，并以 `label / labelFemale` 表达不同称谓；在已检索代码中未找到特化驱动的对应实现。最早仓库提交不等于原作者最初版本，不能据此断定作者有或没有该计划。

动态称谓与方向是独立维度：无方向羁绊可以作为稳定载体，有向关系也可以动态命名。是否保留、扩充或重置旧关系，需要未来重新讨论，不从这项假设直接推出结论。

## 6. 兼容性与证据边界

- 保留原版 Def 身份和记录有利于保护原有判断；不代表未知模组的所有行为、页面与通知自动兼容。
- 新 Def 即使零好感或不存档，仍可能影响关系枚举、计数、排序、最重要关系和其他泛化逻辑；复制基础数值也可能重复生效。
- 当前 RJW 已检查的代码既有伴侣关系集合查询，也有对 Lover／Fiance／Spouse 的直接检查；某些通知只读取一个最重要关系。其吸引计算还存在对关系 `romanceChanceFactor` 的连乘。新增关系不能仅靠名称认定已兼容。
- RJW 奴隶身份识别与 SSC 社交称谓并非同一机制。社会关系重构不自动等于身份、行为许可或浪漫行为控制重构。
- 原版和第三方的查询／写入路径不同。改变旧 Def 的方向、取得范围或删除流程，可能影响插件事件钩子、旧档及人格快照。
- 特化、方向、同主、社会关系和玩法权限需要分别定义；显示去重不等于删除基础关系，查询不应隐式补发奖励或改写绑定。
- 本轮未为任何新方案新增运行 Def、源码或补丁，也未执行新增方案的编译与实机测试。原专项测试只覆盖当时基线，不作为本资料中方案已验证的证据。

未来若重新讨论，应先核对届时的实际代码、游戏与依赖版本；本节用于说明资料局限，不建立待执行检查表或开发排期。

## 31. SSC 社交关系拓展与复合社会关系自动合成【待设计】

**记录日期：** 2026-10-15。

**目标：** 扩展 SSC 系统的社交关系表达，保留基础关系记录，并基于已有的 SSC、原版及可支持的模组社会关系自动生成复合展示称谓，使角色之间的多重联系更清晰且更符合 SSC 设定。

明确需求：

- 拓展 SSC 社会关系，覆盖更多与性奴及主奴体系有关的关系类型。
- 以性奴相关社会关系为基础，结合角色之间已有的原版社会关系，自动判定并形成复合展示称谓；不以复合关系替换基础记录，具体组合与名称尚未确定。
- 复合关系应随基础关系变化更新，包括绑定、解绑、改绑及原版关系的建立或解除，保持显示与实际关系一致。

**2026-10-21 补充：复合关系对基础关系的兼容。**

- 自动生成复合关系时，应保留组成关系的含义及必要的玩法行为。即使复合关系在显示或数据层面覆盖了原版关系，也应尽可能使相关游戏系统正确识别其中包含的原版关系。
- 区分展示覆盖与数据替代。优先评估保留基础关系记录、按组合生成展示称谓的方案；若确有必要用复合关系替换基础记录，应分析受影响的关系查询、建立与解除流程，并在必要入口进行代码适配，不能仅凭名称或配置认定已兼容原版判断。
- 核对社交好感、心情、互动、关系解除及其他相关机制，避免基础效果丢失、重复叠加，或关系解除后残留。
- SSC、原版、RJW 及其他关系扩展模组的兼容范围分别记录，不预先承诺全面兼容。保留基础关系语义是明确目标；路线比较已由下文 2026-10-23 的决定收敛为保留基础记录、合成展示。

**2026-10-23 路线确定与范围收窄：仅基于社会关系合成展示。**

- 已确定采用“保留基础关系记录，仅合成展示”的路线。复合称谓不新增直接或 implied 的 `PawnRelationDef`，不保存复合关系记录，也不调用关系建立或解除流程；原版及其他模组继续读取原有基础关系。
- 合成层以社会关系查询为输入，优先将其作为本功能唯一的关系读取接口。这里的“社交页面关系”指社交系统提供的关系数据，包括适用 Worker 推导的关系，不读取或解析页面上已翻译的文字，也不要求先打开社交页。该范围不等于本批将 SSC 全部绑定玩法改为由社会关系管理。
- 合成层不另外读取锁链、身份组件、调教员指派或仪式状态来补充组合条件。现有 SSC 社会关系可按记录存在与否参加组合，不另设“仪式羁绊／已获奖励”事实，也不查询其获得条件、补发记录或调整既有效果。
- 调教员暂不纳入：当前没有对应的可由社会关系查询取得的专门关系，本批不为组合读取指派数据，也不增加调教员社会关系。
- “同主关系”保留为候选：先判断能否仅从有明确方向的基础社会关系可靠推导；也可另行设计一个专门的同主社会关系。独立基础关系的新增不等于为每种复合称谓新增关系记录，其建立依据、效果及维护成本仍需单独设计，尚未决定实装。
- 当前数据存在方向缺口：`SSC_FlawedLovers` 以同一 Def 双向保存，现有主从称谓依靠锁链额外确定方向；该社会关系本身不能区分主人与性奴，也未覆盖全部实际绑定。只读现有社会关系时可以组合无需主从方向的称谓，不能据此恢复完整归属，更不能仅凭共同关系对象推定同主。
- 有明确主从方向的基础社会关系已在下文 31.1 细化为设计草案，尚未实装。建议由绑定流程维护基础社会关系，锁链读取留在基础关系维护层，合成层仍只读社会关系；这不把社交记录改为绑定权威，也不默认迁移现有奖励关系、改变其覆盖范围或扩展其获得条件。
- 复合展示只收拢自己明确表达的来源关系，其余关系继续显示；好感说明保留原始效果来源，复合称谓不复制或增加组成关系的数值。缺少方向、规则或外部适配时保留基础展示，不按性别、翻译文字或不明确的关系路径猜测。

### 31.1 有向基础主从社会关系设计草案（2026-10-23，未实装）

本草案细化上一段的方向缺口，推荐采用“一条直接记录、一个反向推导关系”的结构。它们是表达真实归属的基础社会关系，后续复合称谓仍仅在展示层合成。以下 Def 名与优先级为建议值，不代表已新增运行定义或完成验证；新增范围仅针对 1.7，1.6／Common 冻结基线不变。

| 建议 Def | 含义：当前查看者眼中的对方 | 存储与查询 |
| --- | --- | --- |
| `SSC_BondMaster` | 对方是我的主人，显示“主人” | 直接关系，`implied=false`、`reflexive=false`；仅从属一侧保存到主人一侧 |
| `SSC_BondSlave` | 对方是我的性奴，显示“性奴” | 推导关系，`implied=true`、`reflexive=false`；Worker 仅检查对方是否通过 `SSC_BondMaster` 指向当前查看者，不另存反向记录 |

方向示例：乙绑定甲，则仅保存 `乙 --SSC_BondMaster--> 甲`。乙查看甲时命中主人关系；甲查看乙时命中性奴关系。名称描述对方，而不是当前查看者。性别只用于翻译所需的语法变化，不参与主从判断；基础称谓不使用“完美”等培养程度描述。

选择该结构的依据是原版已支持“直接 Parent、推导 Child”的关系表达。当前本机 1.7.4985 rev1269 的 XML 与 `PawnRelationWorker_Child.InRelation` 已核对；只借鉴存储与反向查询结构，不复制其亲属语义、生成或数值配置。相比保存两种非对称直接记录，本方案不需要同时维护一条独立的反向社会记录；原生关系接口仍负责维护双方关联索引。

**数据约束与查询接口。**

- 每个从属最多具有一个有效的 `SSC_BondMaster` 目标；同一个主人可以被多个从属指向。两端应具备关系追踪器且不是同一个 Pawn；目标销毁或丢弃时不构成有效关系。死亡、离图、商队或不同地图本身不使关系失效，沿用当前绑定边界。
- 基础关系不增加新的绑定资格，也不据此建立多级归属或循环绑定。若既有／外部状态出现这类情况，本功能不自行推导传递所有权、改变身份或强行重组锁链；分别呈现有据可查的直接方向，并在影响唯一性时报告冲突。
- 查询服务建议提供“读取社会关系中的主人”“判断这对角色的方向”“列出社会关系中的从属”。输入只来自关系追踪器和上述 Def，反向 Worker 不调用锁链、身份、仪式或展示合成器，也不递归调用整套 `GetRelations`。
- 主人查询区分无记录、唯一有效目标和多目标冲突；多目标时不按枚举顺序任选一个，反向 Worker 同样仅接受对方的唯一有效主人。无记录仅说明社会关系中没有主人记录，不应被其他玩法直接解释为已经解绑。查询及 Worker 均不修复数据。
- 从属枚举优先使用原生 `RelatedPawns` 提供候选，再逐一核对其有向直接记录；不为每次界面查询扫描世界角色。具体集合的枚举／去重方式在实现时核对原生接口。
- 主人一侧的性奴关系是 implied 关系，调用方应使用完整关系查询或专用只读接口。只遍历主人 `DirectRelations` 的第三方不会自动得到它；这是明确的接入边界，不通过再存反向记录掩盖差异。

**覆盖范围与现有关系共存。**

- 新基础关系覆盖每一条符合当前绑定有效性规则的锁链，不要求先取得 `SSC_FlawedLovers`，不增加好感或培养门槛。未完成相关仪式的绑定也可以通过社会关系读到明确方向。
- 原有 `SSC_FlawedLovers` 保留原 Def、已有记录、获得条件、解绑清理和效果；既有好感与同床判断继续沿用原入口。新基础记录不会补发该关系，也不会把它认定为原版恋人关系。
- 普通绑定只显示“主人／性奴”；与配偶等关系同时存在时，后续展示规则可合成为“配偶·主人／配偶·性奴”等待定称谓。若旧 SSC 关系也存在，避免在社交行重复显示同一个角色称谓；好感解释仍保留真实来源，不把原有加成转移到新基础 Def。此项是展示去重，不删除旧记录，也不新增仪式状态输入。

**默认配置与兼容边界。**

- 两个新 Def 的 `opinionOffset=0`、`romanceChanceFactor=1`；不设血亲标志、近亲修正、死亡／出售等思想，不参与随机关系生成。`removeOnDeath=false`、`removeOnLeftBehind=false`，与当前绑定在死亡和离图时保留的规则一致。
- `importance` 建议先取 50，作为较低的全局关系排序值，避免通过新 Def 抢占已有婚姻、亲属或旧 SSC 关系。复合称谓的显示优先级单独配置，不提高此值来实现 UI 排序。
- 新增基础 Def 仍会出现在完整关系枚举中，可能改变“是否有关系”、关系数、单一最重要关系和第三方通知；零数值只避免本功能主动增加加成，不代表行为完全无影响。保留原版 Def 身份与记录，逐项检查原版、RJW 及目标模组相关入口。
- 基础主从关系不自动赋予原版恋爱、婚姻、血亲、RJW 奴隶身份或行为许可；这些系统继续按各自规则判断。

**写入权威与生命周期。**

锁链仍是绑定维护的依据。社会关系是对外查询投影，供社交展示和组合规则读取；首批不将 SSC 全部玩法改为读取这份投影，也不将外部社会关系编辑解释为绑定命令。建议将写入集中为 `ReconcileBondSocialRelation(slave)` 一类幂等维护入口：先确定当前最终锁链目标，再仅移除不符的本功能直接记录、保留正确记录并补齐缺项，使用原生 Add／TryRemove 接口，不直接修改关系列表；不反复删除再添加已正确的记录，以免重置关系建立时间或重复触发其他模组通知。

| 场景 | 建议维护结果与时机 |
| --- | --- |
| 新绑定／重复绑定 | 在绑定流程完成或退出时按最终状态核对；补一条正确的直接记录，重复调用不增记录、不改变正确记录的建立时间 |
| 改绑／绑定中途失败 | 在统一变更范围结束后读取实际最终目标，移除旧主人记录并补齐当前目标；不以请求参数宣告成功，不因中间状态另发奖励或关系结束事件 |
| 解绑／直接移除锁链 | 复用正常解绑与健康变化维护入口；若旧链移除后仍有同主新链，保留新链对应关系；不依赖死亡角色的健康 Tick |
| 外部直接改锁链 target | 在已覆盖的健康通知或锁链变更检测阶段统一维护；绕过通知的直接写字段仍有检测延迟，不宣称暂停时必然立即同步 |
| 外部直接增删社会记录 | 不反向修改锁链；监听本功能直接记录的原生增删通知，将受影响从属加入待维护集合，处理重入并合并重复通知；绕过原生接口的改列表行为需要局部复查或读档校正 |
| 旧档／读档 | 引用恢复完成后，复用加载期角色遍历，按有效锁链补齐新记录并移除错误投影；不依赖旧奖励记录推断方向，不补发奖励，不逐 Tick 扫描世界 |
| 死亡／离图 | 保留记录，不将这些事件等同解绑；销毁或丢弃按既有有效性规则撤去有关投影，维护前收集受影响角色，避免丢失定位依据 |
| 人格保存／恢复／克隆 | 新投影不作为独立人格历史转移；保存关系时排除新直接 Def，恢复时过滤外部／旧快照内的同类记录，待身体绑定与普通社会关系全部恢复后统一重建；克隆亦按新身体实际绑定重建，不自动让旧从属改认新身体 |

现有 `ExcretionUtility` 在恢复绑定后会清空并重建社会关系，因此仅在 `Bind` 末尾补记录会被后续步骤清掉；人格恢复的最终出口必须覆盖投影重建。人格排泄等其他清空关系流程也要在业务完成后核对仍留在身体上的实际绑定，避免只处理植入路径。同步期间应延迟相关展示缓存刷新，并对原生增删回调设置重入保护；首次迁移新增记录仍会产生正常关系通知，不能承诺对第三方不可见。

**同主关系与首批验收。**

有向基础关系齐备后，可以只查询甲、乙各自的唯一主人；两者非空且相同、甲乙不同，才能认定同主。多目标冲突时不生成同主结果。是否将其注册为专门 implied 社会关系仍另行决定，本批不保存从属之间的两两关系，不推导主人的配偶或其他亲属也拥有从属。

实现阶段的首批验收包括：无旧奖励也有明确方向；双方视角及各性别一致；一主多从与多目标异常；重复维护不增加记录或重置建立时间；改绑只改变必要方向；原版基础关系及原有效果不变；原生接口与绕过接口的外部编辑分别验证；死亡、离图、销毁、旧档补齐、人格排泄／植入和克隆均按最终绑定核对。展示合成开关不得建立或移除这些基础记录。通过模型或编译检查不能代替上述游戏内验证。
