## 2. 写作需要知道的现有规则

### 2.1 只写当前性奴本人经历，不扩展其他角色心情

心情事件只表现受控性奴本人的综合感受。它已经合并“受到控制／遵从命令”以及这次行为成功、被拒或关系结束的结果；不要再拆成一条服从感受和一条失恋感受。主人、求爱对象和既有伴侣的额外心理／社交好感不在本次范围。

受控接受和受控拒绝表示规则接管了本次回应；即使原版本来就会得到同样结果，也会进入该受控分支。因此不能仅凭“受控”就写成本人原本必然反对／赞同。好感档位与本条综合数值提供情绪方向，不能替代真实爱情或婚姻状态。

### 2.2 四层顺序及阶段名称

事件文案按 **事件 → 锁链阶段 → 是否为有效受虐狂 → 互动前好感档位** 一一对应。文案分支独立于数值，相同数值也不合并入口；不同分支应有可辨认的名称和描述差异。

### 2.3 时长、历史及归组对文案的影响

事件通常持续三天，符合第 8 节条件的负面事件持续 25 或 30 天；同一分支短／长期共用文案，所以不要在正文硬写“只有三天”“整整三十天”等固定期限。零值事件不生成记忆，但仍保留独立文案入口并可能结清旧条目；不能删掉零值行。零值持续思想仍是有效状态，需要正常文案。

## 4. 参数、叙述视角及不可虚构的信息

| 文本层 | 叙述方式 | 当前参数／语法 | 需注意 |
| --- | --- | --- | --- |
| 心情名称／描述 | 受控性奴本人的感受，可用第一人称 | 默认可全部写成不含参数的文本 | 现有分支占位没有人物参数；不需为每行强加姓名 |

| 心情描述 | 同上 | 正常 Worker 路径只保证命名参数 `PAWN`，指具有该心情的性奴本人 | 不保证 `OTHERPAWN`；无主人／下令者参数，不能自行加入 {MASTER} 等 |
| 社交日志 | 以本人为观察入口的第三人称叙述，保留原版日志正文 | [INITIATOR_nameDef] 是行为发起者；[RECIPIENT_nameDef] 是接收者 | 本人视角不是第一人称对白；三类日志的“本人”角色不同 |
| 任务报告 | 正在执行的简短行为描述 | 原样保留 TargetA，由原版解析为任务目标 | 不要写成 {0}、[TargetA] 或任务已成功 |
| 命令结果提示 | 说明真实终态 | {0} 执行性奴短名；{1} 目标短名；{2} 第 13 节行为短名 | 不把 {0} 当成主人；不添加未传入的 {3} 等 |

事件记忆的名称和描述不是同一个参数入口：名称明确先格式化互动对象的 `{0}`，描述正常走 `ThoughtWorker.PostProcessDescription(pawn, text)`，本机原版实现仅提供 `PAWN`。代码中无 Worker 时的描述回退虽然可能提供 `OTHERPAWN`，也不能把这个异常回退当成正式稿的通用参数。持续思想没有互动对象，名称也没有事件记忆的对象 `{0}` 格式化步骤。中文稿可以全部不使用人物参数；若使用，应先确认当前显示入口实际提供的参数，不把三个入口互相套用。

日志没有保存命令下达者，也没有按阶段／受虐狂／好感展开文字分支。不要引入 [MASTER_nameDef]、[COMMANDER]、当前主人名字、特定阶段或心理强度等参数；代码没有向这些规则传值。双方同时受控时，同一互动只有一条原日志，各自视角只附自己的受命／受控事实，不能把另一方背景也写进来。

日志是对原版正文的补句，重点说明受命／受控，不需要重述整段原版求爱过程、再宣布一次所有原结果。原版信件生成时使用发起者视角，因此只会带入发起者的受命背景；不另写十三封信。已有信件保存发出时文字，不会随新稿改写；旧日志／记忆保留事件身份，重新显示时可能使用更新后的译文。

XML 落地时保留键名、规则左侧根、固定索引、TargetA 与现有格式参数；只替换正文。写成 XML 需要转义 &、<、> 等字符，规则分隔符 -> 在 XML 中保持 -&gt;。纯 Markdown 稿先清楚标注键和正文，不必为预览主动改代码。
