# 测试编写与执行准则

**整理日期：** 2026-10-27。适用于本仓库后续测试的新增、修改、精简、执行与结果记录。依据维护者对测试膨胀的反馈及[第27项测试精简](../Completed/第27项测试精简实现与验证.md)整理；具体入口、范围参数和登记方式见[测试说明](../../../Tests/README.md)。

## 1. 基本原则

测试的目标是检出有实际影响的故障，控制维护与执行成本。**不以测试数量、分支覆盖率或输入组合穷举作为质量目标。** 不默认给每个函数、判断分支、XML字段或文案键编写测试；可逆、低影响的修改通常不需要新增用例。

优先复用已有机制回归和统一资源检查。新增前判断：可能发生什么真实故障，现有检查是否已经能检出，新测试是否只是在复述实现或复制资源内容。如果只能证明“文件仍等于我刚写下的字符串”，通常不值得长期保留。

## 2. 文案、XML与资源怎么验证

| 变更 | 默认验证方式 | 不应默认增加的工作 |
| --- | --- | --- |
| 纯文档 | 本地链接／锚点、差异与空白检查 | 构建、机制回归 |
| 普通标题、名称、描述及翻译替换 | XML语法；涉及参数时核对键和占位符；有镜像时使用已有镜像脚本 | 每语／每键单测、完整原生宿主回归、生产DLL重编 |
| 资源路径、语言注入或格式化逻辑改变 | 针对改变的解析／注入／格式化边界做最小验证 | 逐条快照所有正文、无关机制全量回归 |
| XML中的机制配置改变 | 验证配置对实际消费者的影响，选择代表性正常／失效边界 | 把全部参数表复制进测试，再逐格比较 |
| 生产机制改变 | 相关行为、保存与生命周期回归 | 为无关分支和全部组合补测试 |

单纯替换合法正文通常不会改变机制。XML语法正确仍不等于翻译注入路径或格式占位符正确，但这些应通过轻量资源校验解决，不能作为扩大机制测试数量的理由。**文案XML与机制配置XML分开判断，不能因为文件都叫XML就采用同一验证强度。**

Def／语言镜像复用 `Scripts/Test-DefMirrors.ps1` 和 `Scripts/Sync-LanguagesMirror.ps1`；不要在每个业务套件中重复比较同一批文件。必要的已确认原稿逐字核对可做一次性校验，不为44项文案建立44条永久快照用例，也不把字段数量报告成测试数量。

正常文案更名不应使机制测试失败。例如档位可以由“四档”改为设定化名称，不能要求显示文本必须包含“四／IV／4”。确实需要验证显示逻辑时，检查相关状态是否正确呈现，不固定正文措辞。实际字体、换行与界面显示属于相应显示验证范围，不能仅凭字符串断言宣称实机通过。

## 3. 机制测试优先保留什么

优先保留会导致错误效果、状态串用、存档损坏或重复结算的边界：

- 倍率、实际推进量、当前阈值、小数余数、饱和及数值溢出等不同数学边界。
- 同操作去重、重入、异常、中断、真实事件与新周期的清理，避免重复推进或发奖。
- 保存／加载、旧档默认、恢复时序、尚未推进就再次保存，以及实际被内部捕获的构建失败。
- 身体、人格、Comp、锁链、主人、Job或驱动替换后的归属与旧请求拒绝，回调不能为旧上下文重新授权。
- 已经发现并能复现的实际故障；修复后的回归应针对该故障的触发条件。

测试应尽量执行生产逻辑。替身只提供必要环境边界，不复制一套业务算法当作被测对象；预期结果依据独立的行为契约或明确例子，不能从同一实现重新算一遍来自证正确。

独立宿主隔离了地图、图形或第三方副作用时，应明确记录。方法调用、原生Scribe或Harmony路径验证有其价值，但不能替代完整世界存档、游戏内显示或全部模组组合验收。

## 4. 怎样减少重复组合

同一处理路径选择能代表不同故障的输入，不为参数换了一个普通数值就再写一例：

- 普通推进保留零量、单位量、非1推进及必要的极端整数边界，不再追加任意普通减量。
- 阶段限制保留不裁剪、裁剪到最低／中间阶段、恢复原选择等代表，不默认展开档位×阶段全表。
- 相同序列化路径保留无记录／旧档与合法端点，真实不同的恢复生命周期另测，不把每个中间枚举值都保存一遍。
- 非法输入按有限性、区间、类型／结构或归属等不同失败原因选代表；NaN和无穷若只触发同一拒绝逻辑，通常不必全部枚举。
- 多个适配入口共用同一消费者时，入口测试验证真实接入，消费者测试验证统一算法，不在每个入口重复整套数学矩阵。

不能为了减少数字，把原有穷举循环全部塞进一个大 `Check`：这只改变计数，没有减少执行或维护成本。真正精简应删除重复输入、重复断言及不再使用的夹具／分支，同时保留可定位的失败名称。

删除前确认关键行为仍有覆盖，但不要求为了证明删减正确而再新增另一套同等规模的测试。第27项的62项精简是上述原则的一次实践，不是后续任务的删减配额或数量上限。

## 5. 怎样选择执行范围

按本次改动选择最小但足够的验证范围。纯文案优先静态资源检查；机制改动运行相关套件或相关分区。**已有宿主没有方便的文案入口，不是运行整套数百项机制回归的充分理由。**

相关检查通过后即可继续交付。只有新修改、失败或尚未解决的具体风险才扩大或重复测试；不为了“多跑一些更放心”反复运行已经通过的相同范围。

跨模块公共契约变化、相关检查无法排除广泛影响，或进入正式发布门禁时，再按仓库规则扩大验证。统一入口默认All、发布强制All的契约保留，但不意味着每次编辑都运行All。单个套件的All不等于整仓All，Core／Special子集也不能冒充完整门禁。

修改分流或初始化时，要保证所选分区能独立运行，不依赖先执行另一条被排除的用例。删除检查时同步清除 `Tests/TestProfiles.json` 中对应的专项名称；业务测试不为资源初始化而保留一条无关的文案测试。

## 6. 计数、证据与维护

结果记录须说明实际执行范围、通过／失败、是否构建及所用产物。区分以下数量：

- 本次新增／删除的用例，与套件原本已有的用例。
- 实际运行项，与登记总数、字段数、文件数和断言数量。
- 自动回归、源码取证、实机反馈和统一／发布门禁。

例如报告“625项通过”时，应能说明哪些是该功能、哪些属于宿主中的既有功能；不能让读者误以为文案修改新增了625条测试。多个参数输入分别执行时按实际次数计数，不以合并名称掩盖数量；既有同名报告项与唯一名称数量不同，也要明确区分。

增删后同步维护实际用例、范围登记、测试README及相关实施记录。全仓登记若仅根据历史基线加减，应注明未执行整仓全量；历史结果保留原时点，不能将其改写成本次通过结果。长期准则不固定当前测试总数，以[测试说明](../../../Tests/README.md#测试范围与计数)的现行登记为准。

测试通过不自动授权同步游戏、替换正式DLL或发布。构建、提交、同步和发布按当前任务范围执行，文档维护本身不隐含这些动作。
