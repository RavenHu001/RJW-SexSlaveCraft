## 3. 共用事实确认与消费次序

新增 SSCRomanceInteractionFacts.TryConfirm，复用原 SSCRomanceMoodFrame 的原人格、组件、关系载体、实际接受 bool 和原 worker 完成证据。事件／阶段／受虐狂／好感心情目录、原版心情准入和替换账本均不作为事实确认条件。

确认顺序：原 worker 确实运行且无异常 → 原人格及关系载体仍有效 → 双向最终关系与接受／拒绝／拒婚分手见证一致 → 再检查原人格 → 冻结双方受控事实。未发生、直接无共同入口调用、跳过、异常、人格失效或结果不确定不创建事实。

十三类事件继续使用原 SSCRomanceCompositeEvent 稳定编号；每条事实只保存事件和互动前关系，行为及是否拒绝由事件派生，不另存一套结果 bool，不携带分支值、阶段、特质、好感、时长或命令权限。心情按事实事件继续选取完整分支表；这不是新增十三套数值。

求婚三个语句包 Add 的见证移到独立 Harmony_SSCRomanceProposalFacts，原生 Add 本身照常执行。锚点整体失配保留原代码；实际卸载后 Ready 失效。缺乏拒婚／附带分手证据时不猜测完整结果，也不新增随机调用。心情账本原有 Worker 钩子只观察心情，不再兼任求婚结果见证。

SSCRomanceMoodEvents.Finish 先冻结事实，再沿原心情载体及 NativeMoodHooks.Ready 进行心情结算。SSC 准入被拒、零值、没有心情需求、心情载体变更、原版心情观察缺失或工厂失败，不撤销已经确认的日志事实；心情本身仍按原有安全边界保留原版／旧历史。原来仅供日志返回的 ActorEvent／TargetEvent 及 Award 背景返回值已移除，保留实际心情回执诊断。

同结果的有效禁止／强制接受仍形成受控事实；普通允许透传不形成受控背景。阶段与五语义组数值、准入后更新、零值结清、关系阶段清理及保存顺序不改。

## 4. 同一条日志与历史保存

PlayLogEntry_SSCRomance 保存双方各自 SSCRomanceInteractionFact，替换原先依赖心情成功回执的背景载体。工厂精确匹配原参与者、已确认帧和实际互动行为；无受控事实或行为不匹配时使用原版条目。双方同时受控也只有原 tracker 创建的一条记录。

本人视角读取事实副本，普通另一方／第三人没有受控本人背景；本批沿原统一占位追加，不在查询时重新判断当前阶段、开关或关系。原版图标、时间、原结果语句包、点击跳转、日志身份及信件引用同条日志继续保留。

原生 Scribe 保存双方事实和既有原参与者／语句包引用；不保存翻译后的文字，不重放互动或发记忆，不签发发生顺序。不存在未发布旧背景格式的迁移或兼容回退。社交日志仍归原世界日志，事实不加入人格记忆或克隆复制流程；普通人格／新克隆浪漫配置规则保持。

## 5. 当前任务描述与命令结果

SSCRomanceCommandPresentation 共用以下展示类别：求爱、求婚、分手、解除婚约、离婚；无可靠原关系时保留通用结束关系回退。调度前在原记录保存纯展示类别，队列／读档不需要查询当前关系或重新领取权限；完成后真实事实优先展示实际发生的行为。

JobDriver_SSCRomanceCommand.GetReport 保留原版显式报告覆盖，然后只读查询原 Job 记录，再由 ReportStringProcessed 解析 TargetA。报告不调用 EnsureClaim、Claim、TryAuthorize、维护许可或发消息，不增加新 JobDef／工作类型，也不改寻路／有限等待／一次下令被打断即结束的语义。

命令正常终态改为消费同一份已确认命令事实：拒绝事件为 Rejected，其余有效结果为 RelationshipChanged；不再用另一个 RelationChanged 检查猜测结果。缺共用确认时保留 Indeterminate／Unconfirmed，不会自动重试。真实 worker／当前 Job／原授权的既有准入与运行守卫继续保留。

一次性反馈仍经 SSCRomanceCommandGameComponent.Feedback，复用 feedbackSent 和被动／原版手动求爱消息去重。复用四个既有 SSC_Romance_Result_* 入口并加入行为参数，新增拒婚且分手结果；原版关系信件与心情原结算照常处理。读档或重复 Cleanup 不补发结果。

四语各新增 13 键：6 个任务模板、6 个专用行为名称、1 个拒婚分手结果；复用并调整原有 4 个结果键，各语言 SSC_Romance.xml 现为 105 个唯一键，源码镜像一致。旧按钮用的 Action 键保留原文字；新反馈使用 CommandAction 键，不相互覆盖。所有新任务／结果均标明临时占位。

### 8.1 发现与修正

- 共用事实要求两端互动前关系快照一致且符合对应行为；拒绝求爱必须仍无当前恋爱／婚约／婚姻关系。原方法返回后的外部补丁建立婚约或婚姻，不能仅因“不是 Lover”就确认拒绝。双向关系查询结束后再读同一关系载体的实际直接列表，防止后一次查询回调改变先前读取的状态。人格及组件校验继续沿原实例，不重新捕获 token。
- 新增命令事实按同一行为、主动角色、有效原关系及既有终态结果校验。完成缺事实、未知事件、错误原关系、被动事实、行为错配、结果矛盾，或 Pending／Claimed 携带历史事实，读档后均记不确定并清除错误事实；不迁移未发布旧记录，不重新执行。真正进入新执行时先清残留结果，本次必须由原 worker 重新确认。
- 任务报告和结果文字读取共用有效事实入口；完成记录不一致时格式化本身使用不确定结果，即使尚未经过读档对账，也不能错误地提示拒婚分手。原反馈去重、原报告覆盖及 TargetA 解析保持，查询不签发命令权限。原命令已有接受观察字段保留原保存契约，但不再作为完成判据或另一份事实来源。
- 日志本人背景同时校验主动／被动归属与原 InteractionDef 行为；错误保存字段或构造参数不会向错误一方展示受控背景。同一条日志的原图标、时间、关系结果语句及信件引用保持。
