## 索引写法与阅读顺序

- 总索引只写用途、版本入口和阅读顺序；提交哈希、逐批计数与实现细节放入关联记录。
- 各分类索引列清文件用途，避免只罗列文件名。开发记录先放完成汇总，再放阶段与修复；设计先看当前状态，再看方案。
- 当前规划、待验收事项和历史资料分别标明状态。归档混合文档时，写明已经交付的范围，以及仍保留在哪里的后续需求。
- 版本引入时间可以保留在章节中；文档整体适用版本与历史基线应明确区分。

## 版本同步

`VERSION` 是当前仓库版本基准，登记与正式发布分别记录。当前开发登记 **2.4.4**，最新正式发布仍为 **2.4.3**；1.7 DLL、BUILD-INFO、About 及源码文件／产品版本仍标记 2.4.3，1.6／Common 冻结于 2.4.1。历史日期、测试和发布产物不回写，见[发布验证](../Releases/2.4.3/2.4.3版本验证.md)。新版本资料链接应固定到实际发布标签，公开附件须经门禁与哈希核验。

开发里程碑登记时同步当前文档并保留原验证依据；准备正式版本时还须同步 DLL、About 元数据和打包工具。若本次明确只改文档与版本标记，应记录运行产物仍持有的旧版本及打包限制，不暗改代码或游戏文案。历史发布记录、测试报告、发布日期和已发布包不回写为新版本。

## 完成与归档

当前示例：SSC 武器首批已交付，统一入口为[完成核对](../Development/Completed/SSC武器拓展首批完成核对.md)，原方案在[设计归档](../Design/Archive/SSC武器拓展首批开发规划.md)，美术与声音在[资源表](../Art/SSC纳米催情液武器资源.md)。分批记录中的旧状态按当时语境阅读，未来第 36、37 项只保留新增范围。维护者后续实机确认写入验收文档，不回写此前构建／同步 JSON 的生成时点字段。

1. 实现后记录已完成范围和验证依据；自动回归与实机反馈分别记录。
2. 将已交付范围的设计移入设计归档，保留原日期与条目编号。仍待开发的内容从当前规划索引继续可达。
3. 尚未关闭的已实现事项汇总到待验收索引，不因已发布而标为全部验收。
4. 已使用过的提示词和交接资料放入历史参考，标明现行定稿入口。

## 移动与链接检查

移动前核对源和目标均位于仓库内。移动后同时修正文档自身的相对链接、其他索引、玩家指南、测试说明和历史记录中的入站引用；保留锚点或同步更新引用。

检查相对路径目标与新增阅读锚点，确认旧路径没有残留，再执行 `git diff --check`。纯文档整理按链接、版本和差异核查；不复用历史测试计数作为本次验证结果。

`Scripts/New-Release.ps1` 按文件白名单打包根目录玩家指南、首页、版本与更新日志；`Docs/` 仅包含模组介绍、玩家阅读入口和当前版本发布说明，完整名单见[发布与打包](发布与打包.md#发布包内容与检查)。不递归收集开发资料、美术备份或历史验证记录。打包副本中指向未随包资料的相对链接默认改为仓库 main 链接，正式发布可用 RepositoryRef 指定版本标签，保留锚点；仓库原文档仍用相对链接。新增玩家必需文档时须显式更新白名单；源码、测试与本地构建报告不会因此进入安装包。
