## 统一验证入口

需要 PowerShell 7、.NET SDK 9（或更新 SDK）、.NET 9 运行时，以及适用于 **net9.0** 的本地 `0Harmony.dll`（已验证 Harmony 2.4.2）。不需要启动游戏，也不会自动下载依赖。进入仓库根目录后执行（替换示例路径）：

```powershell
pwsh -File Scripts/Test-All.ps1 -HarmonyAssemblyPath 'C:\Dependencies\Harmony\net9.0\0Harmony.dll'
```

也可在当前终端设置环境变量，供独立验证和打包共用；显式参数优先：

```powershell
$env:SSC_TEST_HARMONY_PATH = 'C:\Dependencies\Harmony\net9.0\0Harmony.dll'
pwsh -File Scripts/Test-All.ps1
```

脚本按顺序恢复、重新构建并运行全部 16 个套件；无须记忆各套件的路径参数。缺少 SDK/运行时、缺少项目或 Harmony 时标记 `NotRun`；恢复、构建、运行或结果摘要异常时标记 `Failed`；只有正常退出并报告全部用例通过才标记 `Passed`。可运行的后续套件继续执行，最后统一返回结果；任意失败或未执行均返回非零退出码。

Harmony 预检仅读取 PE 元数据，要求程序集名 `0Harmony`、目标框架 `.NETCoreApp,Version=v9.0`；不接受游戏的 .NET Framework/Unity 版本。检查不会把第三方代码加载进 PowerShell。新增 `.csproj` 必须加入脚本中的唯一套件列表，否则整体检查失败，避免新套件被悄悄遗漏。

默认报告目录为 `.builds/validation/<时间-随机标识>/`，包含每套件的 `.log` 和 `summary.json`；可用 `-ReportDirectory` 指定其他位置。汇总记录状态、原因及从执行输出读取的用例数，失败或未执行且未得到有效摘要的套件计数为 null，不把历史 390 项当作本次结果。`-PassThru` 额外返回结构化成功结果，供打包脚本使用。

## 一键生成发布包

打包另外需要 Git。配置好上述环境变量后执行：

```powershell
pwsh -File Scripts/New-Release.ps1
```

默认复用仓库中的 `Assemblies/Sexslavecraft.dll`，适合没有游戏依赖的机器或 CI 重新打包已编译版本。
脚本会校验版本，调用 `Test-All.ps1` 运行全部 16 个回归套件，全部通过后输出：

```text
Releases/RJW-SexSlaveCraft-TieJin-Modify-2.3.0.zip
Releases/RJW-SexSlaveCraft-TieJin-Modify-2.3.0.zip.sha256
```

2.3.0 的 15 套基线共 390 项：`RitualProgression` 29 项、`RitualLifecycle` 40 项（含 UAP 兼容）、`PersonalityTraits` 23 项、`PersonalityMemories` 16 项、`PersonalitySpecializations` 21 项、`PersonalityCardLayout` 18 项、`RaceInjection` 8 项、`InteractionProtection` 27 项、`PersonalityInsertion` 16 项、`GenderChangeMemory` 11 项、`RitualAnimationFallback` 6 项、`PermanentLactation` 22 项、`BusTrade` 30 项、`TrainerIdentity` 30 项和 `SharedBed` 93 项。当前开发增加 `RestrictionCore` 115 项，并将 `InteractionProtection` 扩充至 104 项、`TrainerIdentity` 至 41 项、`RitualLifecycle` 至 50 项，`BusTrade` 至 42 项，共 16 套、615 项；统一入口根据当次输出汇总数量，不写死基线计数。
全部套件使用离线 NuGet 配置。打包可直接传入 `-HarmonyAssemblyPath`，也支持 `-ValidationReportDirectory` 指定报告位置；报告不进入安装包。任一失败或未执行均在创建 staging/ZIP 前停止。历史 2.3.0 的分开运行记录保留在 [版本验证](../Releases/2.3.0/2.3.0版本验证.md)，不改写成统一入口已在当时生效。
无 UAP 类型的 32 项生命周期检查和无动画框架类型的 1 项检查仍为额外可选变体，命令见 [2.2.13 版本验证](../Releases/2.2.13/2.2.13版本验证.md)，不重复计入 390 项。
统一入口现在为保护套件和同床套件强制提供本地 net9.0 Harmony，执行真实补丁注册检查。普通任务的新回归见[阶段 3A](../Development/新限制系统阶段3A.md)，日常与仪式见[阶段 3B](../Development/新限制系统阶段3B.md)。

已存在同版本产物时默认停止；明确需要覆盖时加 `-Force`。
可用 `-OutputDirectory <路径>` 指定输出目录。默认 `Releases/` 已被仓库现有忽略规则覆盖，不提交 ZIP。

## 从源码编译后打包

**修改了 C# 源码后应使用 `-Build`。** 默认复用模式仅检查版本，不能证明同版本 DLL 对应最新源码。
编译需要 Visual Studio MSBuild、.NET Framework 4.7.2 开发组件，以及本机游戏和模组依赖。
脚本从 PATH 或 `vswhere` 自动发现 MSBuild，也支持 `-MSBuildPath <完整路径>`。

项目中的引用路径是旧开发环境路径。可以用 `-ReferenceTargetsPath` 指向本机的 MSBuild
引用覆盖文件，而无需把个人安装路径写入项目。本次工作区已有的覆盖文件支持如下命令：

```powershell
pwsh -File Scripts/New-Release.ps1 -Build `
  -ReferenceTargetsPath .builds/ritual-fix/LocalReferences.targets
```

该 `.targets` 是本机忽略文件，不随 Git 或发布包分发。换机器时需自行创建覆盖文件：
在 `BeforeTargets="ResolveAssemblyReferences"` 的 Target 中，为项目中的
`Assembly-CSharp`、`UnityEngine*`、`RJW`、`Rimworld-Animations`、`0Harmony`
引用设置本机 `HintPath`；或将项目原有引用路径调整为本机可用路径后直接使用 `-Build`。
构建产物只包含本模组 DLL，依赖库不会被复制进发布包。

## 发布包内容与检查

- ZIP 顶层只有 `RJW-SexSlaveCraft-TieJin-Modify/`，可直接解压到 `RimWorld/Mods/`。
- 包含 `About`、`Assemblies/Sexslavecraft.dll`、`Defs`、`Languages`、`Textures`、`Resources`，
  以及存在时的 `Sounds`、`Patches`、`LoadFolders.xml`。
- 包含项目首页 `README.md`、英文入门 `QUICK_START_EN.md`、其余中英文指南、`VERSION`、`CHANGELOG.md`、`Docs`、`INSTALL.txt`。
- 不包含 C# 开发目录、测试、Git/IDE 缓存、PSD 工程、PDB 或第三方 DLL。
  已有 PNG 和 DDS/ZSTD 纹理均保留。
- `RELEASE-MANIFEST.json` 记录每个有效载荷文件的相对路径、大小和 SHA-256，
  以及基础提交、工作区是否存在未提交内容、生成时间、是否在本次重编译 DLL，以及统一验证的套件数和通过/总用例数。
  清单不计算自己的哈希；ZIP 的整体校验值位于相邻 `.sha256` 文件。
- 任一版本检查、编译或回归测试失败都会中止，不生成新的安装包。

验证 ZIP 的整体校验值：

```powershell
Get-FileHash Releases/Published/2.3.0/RJW-SexSlaveCraft-TieJin-Modify-2.3.0.zip -Algorithm SHA256
```

## 自动化原理与实现

脚本将人工发布时的固定步骤按顺序执行。使用已有 DLL 时，流程为：

```text
读取 VERSION → 检查版本与更新日志 → 检查实际 DLL → 运行回归测试
→ 按白名单收集文件 → 生成清单 → 压缩 ZIP → 生成校验文件 → 清理临时目录
```

传入 `-Build` 时，在检查实际 DLL 之前插入 Release 重编译步骤。
脚本本身不推断下一个版本，也不自动编写更新日志；维护者先确定版本与更新内容，脚本负责检查和执行。

| 步骤 | 实现 | 作用 |
|---|---|---|
| 定位与读版本 | 通过 `$PSScriptRoot` 找到仓库根目录，读取 `VERSION` | 不依赖调用者当前所在目录定位源码；ZIP 名称随版本生成 |
| 源文件检查 | 检查三段数字版本、`AssemblyInfo.cs` 属性、About 描述、对应版本的日志标题及运行目录 | 提前发现未同步的版本或缺失目录；玩家指南仍需人工同步 |
| 可选编译 | 查找 MSBuild，调用项目的 `/t:Rebuild /p:Configuration=Release` | 从源码生成要交付的 DLL；本地 `.targets` 只覆盖依赖引用路径 |
| 二进制检查 | 用 `FileVersionInfo` 读取实际 DLL 的文件/产品版本 | 阻止只改版本文本而仍打包旧版本 DLL |
| 回归测试 | 调用 `Test-All.ps1`，预检依赖，离线恢复、重建并运行全部套件，汇总退出码与实际用例数 | 任一失败或未执行均停止打包；输出逐套件日志和 JSON；不启动游戏 |
| 收集文件 | 在输出目录下创建随机 staging 目录，复制允许的运行目录、唯一的模组 DLL 和文档 | 保持安装目录结构，排除开发工程与第三方 DLL |
| 生成清单 | 逐文件计算大小与 SHA-256，记录 Git 基础提交及工作区状态 | 便于核对资源和追溯构建来源；包含未提交改动的构建会明确标记 |
| 压缩与校验 | 用 .NET `ZipFile.CreateFromDirectory` 压缩临时模组目录，再计算 ZIP 哈希 | 生成可直接解压安装的 ZIP，以及独立的 `.sha256` 文件 |
| 错误处理与清理 | PowerShell 错误立即停止；显式检查外部命令退出码；`finally` 校验路径后删除 staging | 失败时停止后续步骤，清理本次临时文件；同版本产物默认拒绝覆盖 |

`RELEASE-MANIFEST.json` 不对自身计算哈希，避免循环依赖；外部 ZIP 校验值覆盖整个压缩包，包括清单本身。
SHA-256 用于比对完整性，不是发布者数字签名。

自动化的边界：

- 默认模式复用已编译 DLL，只检查其版本；同版本源码变更仍需 `-Build`，版本号相同不代表源码与 DLL 一定同步。
- 当前统一入口覆盖 16 套、基线 615 项，包含身份、同床与新限制核心；测试桩和存档字段契约检查不能替代游戏内完整流程、动画或真实存档往返。
- 这是可重复调用的流程，不保证每次 ZIP 的字节完全相同：清单生成时间、工作区状态和 ZIP 文件时间会影响哈希。
- 已有同版本包需显式使用 `-Force` 才会覆盖；脚本在开始压缩前完成版本、编译和测试检查。

## 下次更新流程

1. 修改 `VERSION`，同步 DLL 文件/产品版本、About 描述和指南版本。
2. 在 `CHANGELOG.md` 顶部新增 `## [版本] — YYYY-MM-DD — 更新主题`，汇总该版本实际交付的玩家可见改动；按日期的技术记录写入 `Docs`。
3. 配置 net9.0 Harmony 路径，执行 `New-Release.ps1 -Build`，自动完成统一验证、版本校验和打包；开发时可先单独调用 `Test-All.ps1`。
4. 游戏内验证通过后，将源码、文档及新 DLL 一起提交，再从干净工作区打包发布。

目前自动化覆盖本地编译/测试/打包，不会自动推送 Git、创建远端 Release 或上传文件。
将来可由 CI 安装 .NET SDK 9 并提供 net9.0 Harmony 后调用同一脚本，复用已提交 DLL 生成构建产物；
若要求 CI 也编译模组，则还需准备游戏及依赖程序集。
测试为无游戏环境回归测试，不能替代完整仪式、动画和存档的游戏内验证。
