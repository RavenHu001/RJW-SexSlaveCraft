# 主奴同床机制复盘

检查日期：2026-09-16。仓库基线：`1eaefc3`，版本 `2.2.15`。

本文是优化前的现状检查，不是已经确定的新玩法，也不将现有行为整体重新归类为 bug。维护者此前决定保留同床兼容对恋爱判断的影响；相关回滚记录见 [开发更新记录](../Development/开发更新记录.md)，未来目标见 [开发规划第 15 项](未来内容开发规划.md#15-主奴同床优化调整和可视化)。本次未修改运行代码、Defs、DLL 或存档。

- 检查当前源码、同床 ThoughtDef、关系 Def、绑定/解绑服务与开发记录。

- 当前没有同床专用回归套件；旧套件随上次方案一起回滚。本次没有运行与同床无关的其他套件。

本机检查脚本和 IL 摘要保存在被 Git 忽略的 `.builds/shared-bed-audit/`。其中 `Inspect.ps1` 可重新导出原版 IL、恋人判定调用者及安装 DLL 对比结果；脚本使用本机路径，不是发布工具。

## 3. 当前玩家可见规则

### 3.1 对象与门槛

普通路径要求**当前恶堕严格大于 `0.001`，即 0.1%**；恰好 0.1% 不生效。这里不用历史最高恶堕，也不要求固定的锁链阶段。

同床“主人”实际按以下顺序解析：

1. `ChainOfSexSlave.LinkedPawn`。
2. 没有锁链主人时，使用 `CompSexSlaveTraining.selectedTrainer`。

因此，没有正式绑定但有当前恶堕和指定调教员，也可能获得同床资格。这个工具本身没有再检查 SSC 身份；“原版奴隶身份”和“SSC 性奴身份”在不同入口中也不是同一条件。

`SSC_FlawedLovers` 是另一条床伴判定路径：只要关系存在，就使床伴判定返回真，不要求恶堕门槛。但找主人床、手动增加候选和同床心情仍各有自己的主人/恶堕条件。

### 3.2 找床顺序

原版 `FindBedFor` 先执行，过程中已经会调用被 SSC 修改的床位判定。SSC 后置补丁随后依次处理：

1. 如果有效原版身份是 `GuestStatus.Slave`，且能使用主人的床，**直接以主人床覆盖原版结果**。
2. 不满足上项且原版已有结果，保留原版结果。
3. 原版没有结果时，为有恶堕的原版奴隶扫描普通床，选择通过检查且直线距离平方最小的一张。
4. 仍然没有结果，再尝试主人床。

由此产生的区别：

- 原版奴隶会优先主人床，已有独立床也可能被覆盖。
- 自由殖民者即使具有 SSC 性奴状态，也不走第 1 项强制优先；通常保留原版找到的床，包括自己的床。
- 主人不必在床上；这段逻辑只要求主人拥有床。因此“选择主人床”不等于“已经和主人同床”。
- 没有等待主人就寝、共同作息或跟随主人上床的行为。
- 普通休息任务随后会调用原版 `ClaimBedIfNonMedical`，因此自动选择主人床可能解除原床归属并认领新床。它不是独立于床位归属的临时陪睡位置。

### 3.3 床位容量与分配界面

主人床路径检查主人是否为拥有者、床在同图生成、未燃烧、非医疗/非囚犯床、能否使用该床型、意识形态、按调用参数启用的社会适当性，以及占用/归属槽位。优先找床再检查可达和预留。

手动增加奴隶候选的要求更窄：主人已拥有该床，床至少两个位置，非奴隶床/囚犯床/医疗床，未满员，意识形态允许。新候选只从地图上的原版殖民地奴隶中补充。

普通双人床只有一个主人以外的位置。现有实现没有多个性奴轮换、优先名单、等待队列或固定陪睡对象。有人认领后，其他未分配角色通常会因无空归属位置被拒绝。

候选列表先过滤不符合条件者，故部分人会直接不出现；界面无法统一说明是恶堕不足、无主人、床已满还是床型不符。代码中额外的两条理由（满员、意识形态）还是硬编码中文，且不能覆盖所有拒绝分支。

### 3.4 同床心情

触发情境要求：角色当前躺在至少双人床上，同床占用者中存在其解析出的主人，且角色当前恶堕超过 0.1%。床是否由主人拥有、是否为医疗床，并不在这个情境判断里再次检查。

这段代码**没有检查双方是否真正睡着，也没有累计共同睡眠时间**。只要原版将双方识别为在床上的占用者，清醒躺卧也可能满足条件；仅分配到同一床而没有同时在床上则不满足。

以下优先级从上往下匹配，只有被绑定/被调教的一方获得自定义想法：

| 条件 | 心情 |
| --- | ---: |
| 与当前解析主人有 `SSC_FlawedLovers` | +13 |
| 当前恶堕 ≥ 50% | +9 |
| 当前恶堕 ≥ 30% | +5 |
| 其余且对主人好感 < 30 | -6 |
| 其余且对主人好感 < 50 | -3 |
| 其余且对主人好感 ≥ 50 | +2 |

最高档取决于关系，不取决于最高恶堕或最终锁链阶段。该关系目前在绑定仪式结算中依据性奴对主人好感 ≥ 80 添加，关系 Def 本身又提供 +100 好感。

`SSC_SharedBedWithMaster` 是**情境想法**，没有记忆持续时间，也没有在睡眠结算时添加同名记忆。任一方离床后，后续情境刷新会使它失效；原版的缓存可能造成短暂显示延迟，不应视为持续奖励。

此外，本机原版 Mood 定义启用 `freezeWhileSleeping=true`，`Need_Seeker.NeedInterval` 在冻结时不推进心情数值。因此“睡着时存在 +9 想法”不能等同于“睡一晚稳定获得 +9 的次日心情收益”。清醒躺卧时仍可能影响心情。

### 3.5 卧室/营房负面记忆

`ApplyBedThoughts` 后置补丁在结算当刻发现主从双方同床，便移除该角色负值的 `SleptInBedroom`、`SleptInBarracks` 记忆。正值保留；寒冷、炎热、户外等其他记忆没有被这段补丁清理。

这一免除逻辑可作用于主人和性奴双方，与“只有性奴获得自定义同床想法”不同。

原版会在躺卧期间及结束躺卧时结算床位想法。SSC 没有保留此前同床的记录，所以双方起床先后、任务结束时的姿态会影响结算当刻是否仍能识别同床。是否出现一方免除而另一方保留负面记忆，需要实机复现。

## 4. 优化前需要明确的行为差异

以下是观察到的实现差异和优化候选，不代表已批准改变规则。

### A. 主人床优先级高于医疗与特殊休息结果

`Harmony_SSC_FindBedFor.Postfix` 的主人床分支位于 `if (__result != null) return` 之前，没有判断原版结果是不是医疗床、死眠棺，也没有检查正在接受的医疗/特殊休息需求。

本机原版 `FindBedFor` 明确先处理死眠和医疗休息。符合 SSC 条件时，这些结果仍可能被普通主人床覆盖。建议把医疗/特殊休息、玩家指定床、同床偏好的优先顺序作为首批规则确定。

### B. “普通床兼容”比“与主人同床”范围更宽

`ShouldTreatAsRegularGuestForBeds` 只要求有效身份为原版奴隶并有恶堕，没有要求存在主人。`CanUseRegularBedAsCorruptedSlave` 也不检查主人或 SSC 身份。

重试传入 `GuestStatus.Guest` 只改变函数参数，不会改变 Pawn 的实际身份。本机原版 `BedOwnerWillShare` 仍直接读取 `sleeper.IsSlave`；实际奴隶只要床有空的归属位置，就能通过该项共享判定，无须恋人关系。

所以满足其他原版限制时，有恶堕的原版奴隶不仅可能使用无主普通床，还可能加入非主人的普通床。与此同时，SSC 的手动候选补充主要针对主人床，自动找床与界面分配的范围并不一致。

### C. 同床许可、真正恋人和 SSC 特殊关系未完全分离

`LovePartnerRelationExists` 的改动是全局生效的。本机原版中有 8 个直接调用该函数的方法，涉及找床、扰眠、与奴隶同房的思想、求爱/分手权重、床伴查询等；影响不止床位。

但这不等于创建了原版 Lover/Fiance/Spouse 关系。诸如 `ExistingMostLikedLovePartnerRel` 的直接关系列举仍按原版关系类型运行。因此可能出现部分系统认作伴侣、其他系统找不到对应正式恋人的分歧。

此项已被维护者明确保留，不能把直接删除全局补丁当成已确定的优化方案。若后续调整，需要先决定哪些伴侣待遇继续保留，并分别覆盖这些用途。

### D. 当前心情难以表现为完成共同睡眠后的反馈

情境想法依赖同时在床，却不依赖睡眠完成；睡着时心情数值冻结，起床后情境消失。代码注释提到“第二天”，与实际实现不符。

若目标是让玩家感受到一夜同床的影响，建议独立记录共同睡眠事件，再按时长、对象和当时阶段结算记忆。最短时长、持续时间、是否保留床上即时想法、主人是否也有奖励均尚未确定。

### E. 复制原版判定存在遗漏，拒绝原因会被整体覆盖

`CanUseBedNow` 后置补丁只知道原版返回了 false，无法知道具体拒绝原因。随后 `CanUseMasterBed` 通过就直接变为 true。

已确认的差异包括：

- 本机原版会拒绝对真空敏感角色使用真空值 ≥ 0.5 的床；`CanUseMasterBed` 没有对应检查。
- 优先床搜索没有完整复用 `RestUtility.IsValidBedFor` 对搬运者禁用、重复搬运预留等检查，并使用 `Danger.Deadly` 的可达检查。
- `CanAssignTo` 原版会因体型过大拒绝；SSC 分配放行没有体型/`CanUseBedEver` 检查，而实际使用路径有检查。存在“界面可分配，实际用不了”的路径。
- `CanUseMasterBed` 没有显式要求双人床，也没有排除 `ForSlaves`；双人要求在普通情况下依靠空归属槽位间接实现，和分配/心情入口的显式检查不一致。
- `TryFindNormalBedAsNonSlaveGuest` 将 `ignoreOtherReservations` 传给 `CanUseBedNow` 第四参数，但实际参数是 `allowMedBedEvenIfSetToNoCare`。目前候选已排除医疗床，未据此确认独立玩家可见异常；后续重构应修正该参数语义。

这些边界应分别验证，避免通过一个总放行结果同时改变关系、环境安全和床型限制。

### F. 关系变化、床位变化和心情资格未统一处理

绑定、解绑、换指定调教员没有同床专用的床位清理/迁移逻辑。已经认领普通床的原版奴隶，只要仍有恶堕，可能通过普通床兼容继续使用旧床，即使原主人关系已经改变。

`Unbind` 没有移除 `SSC_FlawedLovers`。仅凭该关系仍可通过全局床伴判定，但同床心情还需要当前主人解析和恶堕，所以解绑或恶堕降到门槛以下后，伴侣待遇与心情资格可能分开变化。

后续应明确：解绑、换主、主人死亡/离图、转为自由殖民者时，哪些归属保持、哪些偏好停止、特殊关系是否保留；不能擅自清理旧存档关系。

### G. 可视化与性能

当前反馈主要是原版床位名单和情境心情，没有显示当前解析主人、解析来源、优先床、失败原因或共同休息进度。

性能上，普通床回退会遍历本图全部殖民者床，并对候选做原版资格、寻路及预留检查，再按直线距离选择；多个查询也重复解析主人和恶堕。但没有性能测量证明其是主要瓶颈，建议先统一正确性与优先级，再按实际调用频率决定是否缓存。缓存需要随床位、关系、预留和地图状态失效，不能长期缓存“可用床”。

## 5. 建议的下一步拆分

1. **确定规则边界。** 正式绑定与指定调教员是否都能同床；原版奴隶/自由殖民者是否一致；保留哪些现有伴侣待遇；是否允许共享非主人普通床。
2. **统一床位决策。** 将关系资格、床本身可用性和偏好排序分别处理；返回“是否允许 + 失败原因 + 关系来源 + 目标床”，供找床与界面共同使用。先确定医疗/特殊休息及明确床位分配的优先级。
3. **明确归属和多人方案。** 临时使用是否认领床位；固定搭档还是轮换；原有配偶和已分配角色如何处理；关系变化如何影响旧床。现有容量规则保持为基线，扩容需另定。
4. **统一睡眠结算。** 若采用次日记忆，记录实际共同睡眠、按明确事件结算并去重；负面卧室记忆免除也使用同一事件记录，避免完全依赖离床瞬间。
5. **增加可视化。** 首版可在角色面板显示主人/候选来源、目标床和失败理由，在分配列表解释候选是否可分配。轮换或进度只有在相应机制实际实现后才显示。
6. **补充针对性回归与实机验收。** 当前实现使用 7 个补丁联动，单测一个资格函数不足以证明找床、认领、睡眠和结算都正确。

上述为实施建议，尚未确定具体数值、界面布局、迁移策略或发布版本。

## 6. 后续游戏内验收场景

| 场景 | 需要观察的结果 |
| --- | --- |
| 正式绑定/只有指定调教员；恶堕为 0、恰好 0.1%、略高于 0.1% | 床伴、候选、实际找床与心情的门槛是否一致 |
| 原版奴隶与自由殖民者，其他条件相同 | 有无不必要的身份差异 |
| 自己已有床；主人另有空位 | 实际选床、旧床是否被解除归属、玩家选择的优先级 |
| 生病/待救援/死眠状态，主人床可用 | 是否保留医疗和特殊休息结果 |
| 无主人但有恶堕；他人双人床有空位 | 普通床兼容的实际范围是否符合最终规则 |
| 双人床已有主人和配偶；多个同主角色；多人床 | 容量、归属、候选消失、竞争和关系限制 |
| 双方同步睡眠、错开睡眠、清醒躺卧、一方提前起床 | 想法是否触发、心情是否推进、免除记忆是否对称 |
| 恶堕/好感跨档；存在或移除 `SSC_FlawedLovers` | 六档数值与优先级是否符合规则 |
| 解绑、换主、换调教员、主人离图、招募后读档 | 床位归属、关系保留、偏好与反馈是否一致 |
| 床禁用、不可达、已预留、体型不合、意识形态冲突、真空 | 拒绝原因在 UI 与实际使用中一致，原版边界未被意外放行 |

现行文档中“第二天显示同床想法”“必须双人及以上床”“保留禁止访问检查”等概括，应在最终规则确定后同步修订到各实际入口的行为；本次只记录差异，不提前改变玩家规则。
