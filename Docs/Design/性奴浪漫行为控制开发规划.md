本规划细化[未来内容开发规划第 35 项](未来内容开发规划.md#35-对性奴浪漫行为的控制待设计)。正文以“已确认”与“暂定／待定”区分用户决定和实施建议；未确认建议不视为最终玩法。

## 1. 已确认的四阶段权限

阶段取当前锁链的实际阶段，不取历史最高恶堕、Trait 等级或主人成长阶段。实际主人取从属侧锁链目标，不以指定调教员、仪式主持者、缰绳名单或社会称谓替代。

| 当前锁链阶段 | 已确认开放范围 | 行为边界 |
| --- | --- | --- |
| 1：见习性奴 | 无影响 | 不改变原版主动、被动或关系结束行为 |
| 2：性奴 | 覆盖主动浪漫行为 | 求爱、求婚、主动分手／离婚 |
| 3：屈服性奴 | 增加被动浪漫控制及两个附加开关 | 接受求爱、接受求婚；“主动仅主人”“被动无法拒绝主人”分别保存 |
| 4：肉便器化 | 增加精确指名发起行为 | 指定对象发起求爱、求婚、分手／离婚 |

第三阶段的“仅主人”是对象类别规则，第四阶段的点名下令是对具体对象的一次性命令，两者分别解锁。

- 只保证受控方执行或接受；自由目标按自身规则回应。
- 分手／离婚是单方面结束关系，没有“接受分手”判定，不要求对方同意。
- 第四阶段只增加精确发起命令，不额外增加“指定第三人以后自动接受”的持久规则或指定接受命令。
- 普通浪漫分手不解除锁链，不删除仍有效的 SSC 奖励关系。
- 规则变化不自动清理已有恋人、婚约或配偶；既有关系与后续互动许可分别处理。
- 本规划不重启第 31 项社会关系重构，不增加复合社会关系，也不改变绑定权威。

## 2. 行为与方向矩阵

“主动”指实际发起本次互动的一方；“被动”指本次求爱／求婚的接收者，不根据性别、关系称谓或主从身份猜测方向。

| 行为 | 第 1 阶段 | 第 2 阶段 | 第 3 阶段 | 第 4 阶段 |
| --- | --- | --- | --- | --- |
| 主动求爱 | 原版 | 主动许可 | 主动许可＋可选仅主人 | 延续；可点名发起 |
| 主动求婚 | 原版 | 主动许可 | 主动许可＋可选仅主人 | 延续；可点名发起 |
| 主动分手／离婚 | 原版 | 主动许可 | 延续主动许可 | 延续；可点名发起 |
| 接受求爱 | 原版 | 原版 | 被动许可＋可选主人接受保证 | 延续，不新增点名接受 |
| 接受求婚 | 原版 | 原版 | 被动许可＋可选主人接受保证 | 延续，不新增点名接受 |
| 未受控伴侣主动分手 | 对方决定 | 对方决定 | 对方决定 | 对方决定 |

“主动仅主人”仅筛选求爱／求婚的目标，不机械拦截与第三人分手。否则原有第三人关系会因对象不是主人而无法结束，与限制新关系对象的目的相反。

“被动无法拒绝主人”只保证受控接收者接受实际主人的求爱／求婚；不自动令主人发起，不让自由主人在接收从属求爱时必然接受，也不等于立即建立关系。

双方均受控时，各自适用当前规则。主动方允许发起，不等于接收方允许接受；接收方接受保证也不能替主动方创建原本没有发起的互动。

## 3. 暂定的配置粒度、默认值与优先级

以下为实施建议，需开发前确认，不是新增的已确认需求。

- 暂定默认全部放行，“主动仅主人”和“被动无法拒绝主人”默认关闭，新增功能不自动改变旧档行为。
- 暂定第二阶段提供三个独立主动开关：允许主动求爱、允许主动求婚、允许主动分手／离婚。
- 暂定第三阶段提供两个独立被动开关：允许接受求爱、允许接受求婚。
- 两个第三阶段附加开关独立保存，不合并成一个“仅主人模式”，不以其中一个推导另一个。
- 暂定“允许接受”仅表示 SSC 不拦截，普通接受结果仍由原版及目标自身适用规则决定。
- 暂定默认只适用于 SSC 性奴身份且具备有效锁链的角色；旧档身份缺失、残链及外部异常身份的处理须复核现有显式身份恢复入口，不自动认领身份。
- 是否提供全局默认模板及显式批量应用另行确定；首版不默认复用现有行为限制模板进行批量覆盖。

暂定主动判定顺序：当前角色／阶段有效 → 本行为主动许可 → 求爱／求婚的仅主人筛选 → 原版可执行性与实际结算。主动许可关闭时，“仅主人”不会主动重新开放行为。

暂定被动判定顺序：当前角色／阶段有效 → 实际主人且主人接受保证开启时作为明确例外 → 其余对象读取被动许可 → 未被阻止时执行普通接受判断。

这意味着主人接受保证暂定优先于被动总禁或相应行为的被动禁止，形成“其他人禁止、主人保证接受”的组合。该优先级需明确展示；若后续采用总开关，不能把“总禁”字面与实际主人例外冲突隐藏起来。

主人接受保证关闭时，主人没有本模块的隐含豁免，仍读取被动许可及普通接受判断。现有另一套行为许可对主人的直接放行不能自动扩展到浪漫控制。

## 4. 第四阶段精确命令

已确认的命令范围为：让受控角色向指定对象求爱、向指定对象求婚、与指定对象分手／离婚。它们是一次性发起请求，不写入永久指定对象规则。

- 暂定命令可覆盖受控发起者自己的主动禁止及主动仅主人限制，仅限本次请求。
- 不覆盖目标的个人被动许可或普通接受判断；目标恰好也受控时，继续独立评估其当前规则。
- 只能保证受控方发起，不能把自由目标的成功率一并改为必定接受。
- 目标死亡、销毁、丢弃、自指、关系状态不适用或无法完成任务时，显示具体原因；“无视条件”的可覆盖边界须按实际入口逐项确定，不执行空引用或无效关系变更。
- 求婚是否允许绕过原本要求的关系前提，以及阶段 4 可覆盖哪些原版社会／数值门槛，仍待单独确认；不因“精确指名”默认获得所有绕过能力。
- 当前已是配偶等不适用情形应有明确结果；分手命令先核对实际存在的对应恋爱／婚姻关系。
- 指令失败或被目标真实拒绝，不记作成功建立关系；符合原版条件的真实失败反馈仍正常发生。

暂定命令预览至少显示：执行者、目标、行为、当前相关关系、本次覆盖的自身规则，以及“对方仍可能拒绝”的适用说明。分手预览说明将结束哪一种关系，而非展示不存在的接受概率。

菜单打开、点击提交、任务开始及实际互动前复查执行者与目标引用、当前阶段、实际绑定、人格 token 和必要关系状态。原主人、旧阶段或旧人格下创建的命令，不得在状态变化后继续获得授权。

在途命令只携带执行所需引用与一次性上下文，不持有未来的自动接受授权；存读档后按恢复完成的当前状态复查。命令认领／完成标记应去重，避免重复点击、读档或 Cleanup 回调多次建立／结束关系和发放反馈。

## 5. 界面规划

暂定在调教页现有“行为限制”区域增加独立“浪漫行为”分组，沿用当前页面与滚动布局，不把浪漫许可混入原有七项规则的含义。

- 第一阶段显示当前不产生影响；尚未解锁的条目灰显，提示需要的锁链阶段。
- 第二阶段开放主动求爱、主动求婚、主动分手／离婚三项；第三阶段开放被动两项及两个附加开关。
- 当前绑定无效、身份不适用、人格替换中、只读角色等原因分别提示，不用统一“不可用”掩盖门槛。
- 同时显示保存偏好与当前有效状态；暂时失效不伪装成玩家已手动关闭。
- 主人例外覆盖被动禁止时，展示实际主人及例外说明；不把指定调教员显示为主人。
- 第四阶段增加点名命令入口与目标预览；候选应显示关系和首个具体不可执行原因。
- 玩家修改的是角色自己的设置；右键与其他菜单必须读取相同策略，不能只靠此面板隐藏按钮实现限制。
- 四语文本按既有工程规范补齐；动态高度、长姓名、窄屏、禁用原因和主从双视角分别验证。

## 6. 存档与生命周期

必须区分持久偏好和实时权限：存档只保存原始个人选择、版本及必要命令状态；当前阶段、实际主人、是否生效每次由当前状态推导，不把推导结果写回设置。

| 场景 | 暂定处理，实施前确认 |
| --- | --- |
| 新角色／旧档缺字段 | 全部放行、两个附加开关关闭，保持加入模块前的行为；查询不生成拒绝性默认 |
| 降阶 | 保留保存值，暂停未解锁的规则；回到第 1 阶段时本模块不影响行为，升级后恢复原选择 |
| 解绑 | 暂停本模块，保留偏好；取消失去当前绑定授权的在途命令，不清普通恋爱关系 |
| 换主 | 附加开关若仍生效则实时读取新实际主人；不保存旧主人副本，不自动分手或向新主人求爱 |
| 主人死亡／离图 | 不自动认定解绑；保留绑定及偏好，实际互动另查存活、位置与可执行性 |
| 外部直接改链／删链 | 覆盖现有锁链变更、离体通知及读档维护；绕过通知的直接写字段有检测延迟 |
| 人格提取／植入 | 设置属于人格还是身体尚未决定；确定归属后再定义采集、清源、替换及最终刷新时机 |
| 新克隆 | 暂定不继承来源命令、实际绑定及控制例外；设置是否复制以人格归属决定为准 |
| 未知配置版本／坏引用 | 保留可诊断数据，禁止误认主人或执行旧命令；回退策略须显式定义并验证 |

人格流程现会先恢复锁链、随后重建社会关系，因此不能只在 Bind 结束时维护浪漫状态。应在完整恢复最终出口按最终身份、链及人格版本核对，避免中间状态取消合法恢复或保留失效命令。

生命周期维护复用现有局部通知及读档遍历，不新增逐 Tick 全世界扫描。只读 UI 和高频判定不修复绑定、不补发 SSC 奖励，也不在查询中覆盖玩家偏好。

## 7. 执行架构与兼容边界

建议新增独立浪漫策略入口，接收实际发起者、接收者、行为及命令来源，返回允许、阻止、保证受控接收方接受等可解释结果。身份／阶段、自然选择、接受概率和关系提交分别适配，共享同一策略。

- 不直接把浪漫枚举塞入现有 `SSCRestrictionPolicy.Evaluate`；其实际主人直接放行位于用途和配置检查之前，会绕开第二阶段主动或第三阶段被动限制。
- 自然随机选择的权重可提前排除无效候选，但共同执行层仍须复查；仅改按钮或权重不足以覆盖直接调用。
- 共同执行层须覆盖原版随机互动、`JobDriver_Romance` 与 RJW 右键社交路径；不宣称已经兼容所有浪漫扩展模组。
- 主人接受保证应进入对应正常成功结算，不能仅给成功率一个较高数值，也不能跳过关系、记忆和其他原生收尾。
- 分手先校验现有关系，再复用完整业务结算；不能对没有恋爱关系的任意人调用原版分手 worker。
- 不以全局禁止 `RemoveDirectRelation` 实现关系维持，避免误拦死亡、人格恢复、外部修复及自由伴侣单方结束关系。
- 按本机实际 Harmony 补丁组合复核顺序；若其他模组替换共同入口或直接写关系，另列适配与未覆盖边界。
- 原版菜单受 DLC／殖民者资格限制；项目自定义点名入口不能只复用原版菜单资格，否则 SSC 原版奴隶身份角色可能无法发起。

仅新增 1.7 编译与资源内容，沿用[1.7 工程](../../Sexslavecraft/SexSlaveCraft_1.7.csproj)独立追加模块的方式。1.6／Common 冻结检查继续作为交付门禁，不修改现有存档身份或重启社会关系重构。

## 9. 关系结算副作用与待定口径

| 情形 | 已知影响与需确认的处理 |
| --- | --- |
| SSC 规则在开始前禁止 | 暂定直接阻止，不伪造一次失败求爱或拒婚，不产生对应失败记忆或拒婚附带分手 |
| 允许互动后真实拒绝 | 暂定保留原版拒绝反馈；第三人仍有自己的决定 |
| 拒婚附带分手 | 40% 分支不能遗漏；算原版关系后果，还是归入求婚者主动分手许可，尚待决定；不得以受控方规则阻止自由伴侣另行分手 |
| 求爱成功清理旧关系 | 原版可能结束旧 Lover／Fiance；它与主动分手许可及对方已有关系规则如何协调，尚待决定，不承诺禁止主动分手即可防止所有旧关系变化 |
| 主人接受保证 | 应沿成功分支处理；是否允许因此解除其他旧关系、如何呈现其后果，需与上一项一起确认 |
| 主动仅主人开启前已有第三人关系 | 保留；不自动结束、改写或隐藏；可否继续求婚由后续互动规则决定 |
| 普通分手／离婚 | 结束指定原版关系，不拆锁链，不移除仍匹配实际绑定的 SSC 奖励，不改指定调教员 |

这些副作用需要在开发进入关系结算前定案；不得通过只改成功率或只删除关系记录回避。范围仍是本模块社交行为，不扩展至其他身体或行为系统。

## 11. 验收矩阵与开发前待确认项

验收至少覆盖四阶段、阈值两侧、两附加开关四种组合、三主动／两被动许可、自然／原版手动／RJW 右键／SSC 点名入口，以及双方均受控与自由目标。

- 第一阶段完全不影响；第二阶段只管主动；第三阶段被动限制和主人例外按约定生效；第四阶段只增加精确发起。
- 有／无 SSC 奖励、普通好感及低好感分别测试，避免 +100 好感掩盖接受保证未生效。
- 分手／离婚覆盖 Lover、Fiance、Spouse 及无适用关系；自由伴侣可单方结束关系。
- 求婚拒绝及其 40% 分手分支、求爱成功解除旧关系、关系／记忆／床位／姓氏等按定案语义验证。
- 退阶、升级、解绑、换主、死亡、离图、外部直接改链／删链、打开旧菜单后状态变化均复查。
- 存读档保留显式关闭值与两个附加开关独立性；旧档缺字段不改变原行为；在途命令不重复结算。
- 人格提取／植入、空壳与新克隆按最终确定的数据归属测试，不借用未确认的通用能力流转默认。
- 不自动清理既有关系、不误改绑定与 SSC 奖励；1.6／Common 冻结与现有功能回归保持通过。

开发前仍须确认：默认值及五项许可的 UI 粒度；主人接受保证与被动禁止的优先级；第四阶段可覆盖的自身／原版门槛；降阶、解绑、换主的偏好与命令处理；人格设置归属；拒婚分手及旧关系解除口径；是否需要全局默认模板。已确认的四阶段结构及两个第三阶段附加开关不因这些待定项被重新解释。
