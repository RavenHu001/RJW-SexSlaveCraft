### 健康清理保留条件

本机构建的 `Game.LoadGame()` 先执行 `FinalizeInit()`，随后执行 `GameComponentUtility.LoadedGame()`；其他组件可能在两个阶段之间修改健康状态。因此两次扫描是否可合并，需要另行证明，首批构想保留原调用。

修复工具只检查缺失部位的 `lastInjury`；调用方仅在实际修复后执行 `DirtyCache()`。原生 `DirtyCache()` 涉及健康、能力、伤口、肖像等缓存，因此应区分“扫描但无修复”和“发生修复”的成本，不能将所有扫描都视为完整缓存刷新。

现有范围不限于人形角色。任何筛选优化都须保留原适用对象，不能为了减少工作量直接排除动物、囚犯或原版奴隶。分散扫描、延长周期和缓存候选名单均需另外分析时效性与失效规则，本方案没有确定采用。

### 共振统计合并候选

| 操作 | 有有效对象时的当前统计遍历 | 候选方案 |
| --- | ---: | ---: |
| `CalculateMasterEmpowermentSeverity()` | 2 次 | 1 次 |
| `GetEmpowermentSummary()` | 4 次 | 1 次 |

无有效对象时当前已有提前返回，不能按表中的比例计算收益。合并只减少重复工作，不改变随绑定数与健康查询成本增长的复杂度，也不预先承诺整体 TPS／FPS 收益。

候选实现是在 `SSCMasterBondUtility` 内用一次 `GetBoundSlaves()` 枚举形成值类型统计结果，包含数量、平均值、强度和阶段。强度计算与说明生成分别在本次调用内使用该结果，不跨帧缓存，不增加长期 Pawn 索引或对象列表。

保持原枚举顺序、数量阈值、平滑与插值公式、累加精度、舍入和显示格式；不额外去重或排序。只需要数量的其他函数不附带计算平均值。现有迭代器仍可能分配，不能把“合并遍历”描述为整个函数零分配。

原生 `Hediff.Severity` 的健康通知受阶段变化等条件控制，同值赋值不等于每次触发完整刷新。跳过同值写入不作为未经测量的主要收益来源。

## 按需采用的采样设计

如果后续代码分析仍不足以判断收益，可在现有诊断窗口提供仅开发模式可见的独立性能入口。采样默认关闭、只保存在内存中，不增加角色或模组设置保存字段；加载阶段可考虑一次性采集下次初始化。入口、操作和采集时长都留待恢复工作时确认。

候选测量分组为：初始化健康清理、读档健康清理、周期健康清理、共振刷新和共振说明生成。报告只描述这些入口，不代表 SSC 总耗时。

可收集的指标包括调用次数、累计／平均／最大单次耗时、访问的地图／角色／健康条目／有效绑定对象数量、修复角色数、缓存刷新次数、当前线程分配，以及采集期间游戏 tick 和墙钟时间。入口耗时包含下游调用；重入和包含时间不能简单相加为全局 CPU 占用，当前线程分配也不覆盖整个进程。

若实现统计器，应使用固定编号和预分配数值槽；关闭时不查询计时器或分配量、不构造字符串，开启时不逐调用创建对象或输出日志。异常通过 `finally` 结束计数但继续传播；会话编号隔离停止、重置和迟到作用域，换档时清理会话，不长期持有角色或地图引用。

报告在查看或复制时生成。低频入口样本不足时只展示实际次数和基本统计，不输出缺少意义的 P95／P99；离线基准可保存完整批次样本后计算分位数。采样工具自身开销必须与目标入口成本分开说明。

## 自动验证与对比方法

后续优先使用可自动复现的检查来验证明确优化，避免让维护者手工搭建大量相同场景。验证层次分别记录，不把模型结果转换为实机帧率结论。

| 层次 | 检查内容 |
| --- | --- |
| 统计器专项 | 默认关闭、关闭时不访问时钟与分配接口、停止／重置／旧会话隔离、异常和重入处理；关闭路径无新增分配 |
| 健康清理专项 | 初始化和读档阶段、＋120 与后续 600 tick 调度、适用对象、正常／异常 `lastInjury`、无变化不刷新、每角色修复多项只刷新一次 |
| 共振差分测试 | 相同输入下新旧数量、平均值、强度、阶段和说明参数一致，覆盖零对象、人数阈值及失效／死亡／异主等边界 |
| 生命周期回归 | 绑定、解绑、换绑、死亡、暂停及读档清理继续及时生效 |
| 原生专项 | 使用实际 1.7 类型核对计算和健康接口，明确地图、通知与绑定边界 |
| 资源与编排 | 实际新增四语、镜像、布局、冻结基线、专项登记和失败阻断 |

`PnaSpacerNative` 已链接生产 `SSCMasterBondUtility`，可扩展数值与原生接口检查，但其 SSC 绑定集合属于测试边界。真实锁链和缰绳清理仍由 `BondRelations` 等生产链路回归承担，集合替身不代表完整绑定流程。

离线对比可参考 [关系概览对比脚本](../../Tests/BondOverviewUI/Performance/CompareLocal.py)，另建与本次候选相匹配的入口。A 侧为分析基线加测量代码，B 侧为相同测量代码加优化；两侧使用一致边界、输入、编译参数和预热方式，保存来源与编译输入哈希。另比较采样关闭／开启，以识别工具开销。

候选数据规模包括有效绑定数 0、1、3、5、8、30、100，以及不同健康列表长度和锁链位置；健康扫描分别覆盖无修复、少量修复与多角色修复。预热后批量运行，至少三轮交替执行两侧，保存耗时、分配、枚举与查询次数。确定性门禁检查结果等价、操作次数和分配；机器噪声较大的计时作为趋势证据，不写死统一百分比门槛。

人工游戏内对照仅保留为可选补充。若未来确有需要，应从现有存档副本和可自动准备的场景出发，固定游戏、模组、速度、界面和采样条件；加载、正常运行与界面观察分开记录，低频入口展示真实样本数。维护者当前没有接下这些手工步骤，不列入待验收清单。

## 恢复工作时的判断顺序

1. 重新检查当前调用链，优先确认可消除的重复计算、枚举、分配和扫描，以及保留行为所需条件。
2. 对具体候选设计最小自动差分测试；按需建立离线基准或开发采样，不默认先建设完整诊断框架。
3. 只有收益依据和维护成本合适时才实施，保持数值、时效性与存档行为；统一回归按实际结果登记。
4. 健康清理若确有显著成本，再单独讨论调度或候选筛选变化，不自动扩大为本批任务。
