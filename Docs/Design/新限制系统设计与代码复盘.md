| R16 | 旧“性奴保护”开关改为“是否启用性奴行为限制规则”，作为新限制系统的总开关，与规则默认值的编辑分开。 |
| R17 | 在设置页面的性奴行为规则默认调整区增加“为所有性奴应用默认配置”操作。执行时为所有性奴应用当前默认配置；有特化的角色再按该特化的默认/强制规则恢复受影响条目，其他条目采用普通默认配置。 |
| R18 | 开放非主人调教后，仍采用唯一指定调教员，不采用优先候选或多人自由接替。本轮不改动有主性奴现有的调教员资质过滤；允许选择非主人不等于放宽候选人的资质条件。实际主人的固定豁免仍按 R4 处理。 |
| R19 | 调教不查询普通主动、被动行为许可，使用独立调教规则；规则控制与界面分类一并拆开。具体任务用途由代码分析映射，不能仅因复用 RJW 基类或接收任务就认定为调教。 |

本轮不实现自我调教、无主性奴玩法、性奴担任调教者、调教与绑定/主人身份的整体拆分。现有首次绑定前的准备过程仍须兼容，不能因为无主玩法暂不实现而忽略它。

R4 是有方向的绑定豁免：主人 → 自己的性奴放行；反向仍判断性奴的主动许可，其他主人的身份也不构成豁免。多人场景逐个发起者判断，第三人不能继承在场主人的豁免。这里的放行是 SSC 限制层的放行，不负责使无效目标、不可达任务或不满足 RJW 能力条件的任务成功。

## 2. 设置结构与建议的解析方式

以下是统一规则结构；普通初始值采用第 2.1 节基于旧默认保护的分析基线，特化仅声明受影响条目的覆盖，标签与适配细节随实施落实。

| 大类 | 独立规则项 | 说明 |
| --- | --- | --- |
| 主动 | 单人自慰 | 不查询主人是否等于行为对象。 |
| 主动 | 发起双人自愿行为 | 控制是否允许发起；允许时分为“仅限主人”和“不限对象”两档，与接收方许可分开。 |
| 主动 | 发起强制行为 | 按统一主动限制管理；公交车的被动接受规则不覆盖发起方的限制。 |
| 被动 | 接受非主人自愿行为 | 主人发起先适用 R4。 |
| 被动 | 接受非主人强制行为 | 许可之外保留防护装备的额外拦截，按 F5 分析方案处理；主人固定豁免优先。 |
| 调教 | 接受非主人调教 | 独立配置，不叠加普通主动/被动许可；结合唯一指定调教员、既有资质和首次绑定准备边界判断，任务映射见 F2。 |

主动双人自愿行为的有效状态为：禁止发起、允许且仅限绑定主人、允许且不限对象。后两者是“允许”之下的对象范围档位；“不限对象”只解除发起方的对象范围限制，仍需通过接收方许可和任务正常条件。禁止性奴主动发起不会阻止其主人向它发起行为。

旧版本升级按 R14 一次性复制初始化；新角色按 R15 在首次满足适用条件时复制当时的默认规则。两条初始化路径完成后均保存独立个体配置，运行时不再回退读取当前全局默认。激活由适用条件触发，不能只在打开限制子窗口时初始化，也不应无条件在所有 Pawn 刚生成时提前复制。

**初始化与行为判定分层：** 在角色首次满足适用条件的生命周期入口完成 R14/R15 的初始化，再供行为查询读取；身份设置、有效绑定建立、载入后的迁移协调以及新克隆/人格恢复完成等入口共享同一初始化服务。不能只等第一次行为、打开 UI 或 `CompTickRare` 才初始化，否则期间修改全局默认会改变本应已确定的配置。总开关关闭、主人豁免和没有正在执行的行为都不能跳过首次适用时的数据初始化。人格恢复和克隆创建的中间状态仍按 F7 延迟到完整操作结束处理。

入口适配器负责还原上下文并兜底确保配置就绪；纯规则模块只读数据、返回结果，不改身份、指派、特化、基因或初始化标记。建议判定顺序：

1. 检查系统总开关；关闭时返回限制暂停。此时角色配置已经由独立生命周期入口管理，不因此延迟初始化。
2. 规范化任务用途、行为类别及方向；明确单人或双人，识别需要检查的适用角色。信息不足单独返回“上下文未就绪”，不能把空目标当作自慰或默认允许。
3. 对已确认方向的双人任务检查实际绑定主人固定豁免。豁免只跳过 SSC 限制，正常任务资格仍由调用端校验。
4. 解析适用角色的个体值：全局特化强制开关开启且当前适用的文件定义强制值 → 已保存规则值。普通全局默认只参与初始化或显式批量应用，不参与逐次判断；特化默认的其他一次性写入事件按 F6 处理。角色不保存独立的强制开关。
5. 按用途选取对应规则组；普通双人行为检查发起方与接收方，单人只检查自身，调教按 F2。非主人普通强制行为还须通过 F5 的装备检查，不能因某项许可为允许就提前整次放行。
6. 返回允许/拒绝/上下文未就绪及具体原因、来源。已接管且涉及适用角色的任务在真正开始前仍无法还原必要上下文时，应中止本次未开始任务并记录适配原因；不以未知上下文给无关任务增加限制，也不将尚未适配的兼容组宣称已接管。

持续继承全局默认的方案已排除。全局特化强制开关关闭时，对所有角色跳过强制层，保留个体原选择；重新启用时恢复适用条目的覆盖，不改写存档中的原值。特化强制和特化默认在 Mod 文件中分别声明；公交车默认写入事件见 F6，不能以每次查询重写默认的方式代替强制层。

系统总开关按 R16 保留为全局运行控制，不复制成角色的独立启用状态；此前将它一并归入初始化默认值的方案取消。“修改默认值不影响已激活角色”约束的是默认配置编辑，不是系统总开关。建议总开关统一控制行为许可、非主人调教许可及装备防护，特化强制层也受其控制：关闭时暂停这些限制，保留个体配置；重新开启时按保存配置恢复判断，不重置为当前默认。原有身份、主持资格、唯一调教员工作指派及任务正常条件不因此取消，具体区分见 F3。

特化强制开关已按 R8 确认为全局 Mod 设置，此前的角色级保存方案取消。修改它立即影响所有适用角色的后续判断，当前已开始场景仍按 F8 正常收尾。它不是可复制的个体默认项，不参与人格存储、克隆复制或批量默认重设；角色窗口只显示当前全局强制状态和受影响条目的来源。

具体特化条目由 Mod 文件定义，首版建议使用统一的 Def/XML 声明读取默认值与强制值；不在 Mod 设置界面为每个特化生成完整配置编辑器。本轮只有公交车的两条声明。文件定义随模组加载解析，不额外实现热重载；文件中的强制值在下次加载后参与有效值计算，默认值的修改仍只在 F6 明列的写入事件应用，不覆盖其他已保存选择。

**特化只提供条目覆盖。** 每个 Pawn 仍只有一份统一配置；特化只声明“哪个条目、默认为什么、强制为什么”。未声明的条目表示不参与覆盖，不能按缺省 `false` 覆写。设置界面继续使用主动/被动/调教三类，在受影响项旁显示来源与强制状态，不给每个特化复制整套选项，也不新增每个特化各自的强制开关。本轮仅公交车声明两条，其余特化不提供覆盖。

### 2.1 基于当前默认保护规则的初始值分析

按维护者要求，本节从现行代码出厂保护规则推导并形成首版初始值基线，供新系统实施使用；这些是分析结论，尚未写入运行代码。没有读取玩家本机保存配置作为出厂值；新安装默认与旧存档迁移分别处理。

当前 [Settings](../../Sexslavecraft/common/Settings.cs) 的初始值与 `ExposeData` 缺省值一致：保护总开关为 `true`，`protectNonRapeOwnerOnly=true`，`protectChainedAggressorRape=true`，`protectBusAggressorRape=true`，`allowSexSlaveRape=false`。[Comp_Train](../../Sexslavecraft/Comps/Comp_Train.cs) 的旧个体例外 `allowOthersForTrainingOrSex` 初始为 `false`。

**普通已绑定性奴的初始值基线：** 以下按双方均不触发公交车特化例外、旧个体例外未开启的普通情境推导；首次绑定前仍保留 R5 已确认的指定与准备流程。

| 新规则项 | 初始值基线 | 当前代码依据 |
| --- | --- | --- |
| 允许单人自慰 | 关闭 | 自身作为目标进入非强制主人匹配，自身不等于绑定主人，且旧例外默认关闭，因此被拦截。 |
| 允许主动双人自愿行为 | 开启 | 当前没有禁止全部主动自愿行为，而是限制对象。 |
| 主动双人自愿行为的对象档位 | 仅限主人 | `protectNonRapeOwnerOnly=true` 检查发起方的绑定主人是否等于对象。 |
| 允许主动强制行为 | 关闭 | `protectChainedAggressorRape=true` 拒绝带锁链的发起者。 |
| 允许接受非主人自愿行为 | 关闭 | 同一个主人限制开关也检查接收方归属。 |
| 允许接受非主人强制行为 | 关闭 | `allowSexSlaveRape=false` 时仅按绑定主人匹配放行。 |
| 允许接受非主人调教 | 关闭 | 旧个体例外默认关闭，`TrainerAssignmentUtility.GetForcedMaster` 将已有绑定对象的调教者限定为主人。 |

旧保护总开关按 R16 改名后，出厂状态继续开启。新角色在首次激活时复制当时的默认配置，之后保存为自己的规则，不随后续全局默认值编辑变化；玩家可以修改全局默认，显式批量应用按 R17 处理。上述基线保持“普通角色仅对主人开放普通非强制行为，其他列出的行为默认关闭”，并将原本耦合的检查拆成独立条目。

主人 → 自己的性奴始终使用 R4 的固定放行，不需要另外默认开启一组“接受主人”选项。当前旧策略在部分非默认设置/装备组合下仍可能拒绝主人，新系统按已经确认的 R4 处理，而不是保留这些旧组合。性奴 → 主人则按上表，默认允许自愿行为、禁止强制行为。

**公交车仅覆盖以下两个条目：** 主人无需通过这两个非主人选项；将二者设为允许，即在接收方许可层表达“可接受任何人发起性交”。

| 统一规则中的条目 | 公交车默认值 | 启用特化强制时的有效值 |
| --- | --- | --- |
| 接受非主人自愿行为 | 允许 | 强制允许 |
| 接受非主人强制行为 | 允许 | 强制允许 |

按默认方式应用时，只将上述两项写为允许，之后允许玩家修改；按强制方式运行时，也只将这两项的有效值覆盖为允许，保留底层选择。关闭强制不自动将两项改为禁止或重新写入默认，而是使用已保存值。普通主动规则、单人自慰和独立调教仍读原配置；公交车不替对方解除主动限制，普通任务条件和 F5 装备方案仍独立判断。

这张表是统一配置的两条覆盖声明，不是公交车的完整配置模板。旧代码事实与本轮用途对应如下：

| 旧代码表现 | 本轮处理范围 |
| --- | --- |
| 公交车作为接收方直接放行，包括非主人自愿与强制行为 | 仅将上述两项被动许可默认/强制设为允许，不再跳过整套策略；非主人装备拦截按 F5 保留。 |
| 公交车可自慰、可主动不限对象进行自愿行为 | 保留为旧行为迁移参考，不据此新增公交车自慰或主动行为的专属规则。 |
| 公交车默认禁止主动强制行为 | 按普通主动限制与旧设置迁移处理，不新增公交车专属强制项。 |
| 旧个体例外、公交车方向或 Hediff 解除独占调教者限制 | 纳入旧调教许可的迁移评估，不将“接受任何人性交”自动扩展为“接受任何人调教”。 |

当前策略先检查“接收方为公交车”，随后才检查发起方限制；因此普通已绑定性奴向公交车发起强制行为也可能被放行。反之，公交车发起自愿行为又会跳过普通接收方的保护。这些都是整次行为的旧提前返回，不能机械转换成“某一方的允许覆盖另一方的禁止”。新系统按双向许可分别判断，除 R4 主人固定豁免外，不复刻这种跨角色旁路；这是统一系统带来的行为变化，应纳入迁移说明。

奶牛、宠物等其他特化本轮不添加专属默认值或强制规则，使用角色首次激活时保存的默认规则及其后续个体配置。旧代码选择非公交车方向时会重设旧例外，这属于迁移需要清理的写入行为，不能保留成新系统对这些特化的隐含强制限制。按 F6 分析方案，保留终极公交车状态时，其两项覆盖继续适用，即使当前已选择其他方向。

**全局特化强制开关的初始值基线：开启。** 当前公交车的接收放行不能由个体旧开关关闭，默认启用其两项被动覆盖的强制层更接近旧行为。旧代码没有这个开关，因此这是兼容性分析结论，不能称为直接读出的历史字段。`SetSpecialization` 写旧例外的连带效果不因此成为新强制项。关闭该全局开关后，所有适用角色停止声明项的强制覆盖并使用各自保存值；关闭强制不等于将这两项改成禁止，也不重新写默认。系统总开关关闭时，特化强制层同样暂停。

**旧设置迁移已确定采用一次性复制初始化，不能用上述出厂表覆盖玩家选择：** 例如旧 `protectNonRapeOwnerOnly=false` 的普通角色，原本允许自慰、主动不限对象和接受非主人自愿行为；旧个体例外为 `true` 时也会开放这些行为并允许非主人调教，但不会单独解除强制行为限制。按旧全局值、旧个体值和特化状态确定新旧选项对应值，复制写入新配置后由新系统接管；保护总开关关闭的存档也不能擅自恢复为开启。关于装备、关系豁免和双向检查的新语义变化应单独说明，不能保证逐场景完全复刻。

### 2.2 显式批量应用默认配置

“为所有性奴应用默认配置”是一次性操作，不是持续同步开关。它会覆盖已有个体规则选择；单纯编辑默认值、打开设置页面或读档均不得触发此操作。界面应说明覆盖范围，并在执行后报告实际处理数量。

建议按以下顺序处理每个目标：

1. 复制当前全局行为规则默认配置，替换该角色原有的个体规则选择；不复制或重置系统总开关、全局特化强制开关，不改变身份、绑定关系或特化进度。
2. 根据角色当前适用的特化，为受影响条目应用特化默认值。本轮只有公交车的被动接受规则；其余条目保留步骤 1 的普通默认值。
3. 按全局特化强制开关及当前特化状态解析强制后的有效值。关闭特化强制时仍按本次显式操作应用特化默认，但不强制锁定；强制覆盖与底层保存值分开，避免关闭强制后丢失已恢复的默认选择。
4. 保存结果，通过统一变更入口刷新有效规则、界面及调教者限制。系统启用且已有有效绑定时，若非主人调教许可关闭，则调教者归为实际主人；首次绑定前保留候选主人入口。已开始场景与未开始任务按统一生命周期策略处理。

实现范围应覆盖当前存档内所有适用性奴，不能只遍历当前地图或当前打开面板的角色；多地图、商队、运输中及世界角色的枚举、去重和有效对象筛选需要在实施时核对。所有权或原版阵营身份不能被悄悄用来把“所有”改为“当前殖民地已生成角色”；对象仍须满足第 2.3 节的统一适用条件。尚未适用的角色仍按 R15 在首次适用时初始化，不借此为所有普通 Pawn 提前创建配置，也不修改其他存档。重复应用相同默认值和特化状态应得到相同配置，不重复发放成长或触发绑定事件。

批量操作建议先快照本次默认值与目标集合，再逐个更新，避免一轮操作混用不同默认版本或在枚举中改变集合；报告已更新、跳过、失败数量。总开关关闭时只保存配置和刷新显示，不执行“强制改回主人”的关系副作用；重新启用时再统一校验。没有载入存档时不提供可执行的批量操作，也不留下会悄悄应用到下一局的待执行命令。

批量应用不绕过 R4 的主人固定豁免，也不恢复旧特化的整次行为放行分支。公交车只恢复第 2.1 节列出的两项为允许，并记为已处理该特化默认；其适用状态及批量操作之外的写入事件采用 F6 分析方案。

### 2.3 适用范围、配置存在与规则生效分开

现文多处使用“首次适用”，必须落成同一判断，不能分别借用 UI 可见性、调教启用、研究或恶堕进度。代码中的 `SSCIdentityUtility.HasEstablishedSexSlaveState` 还会认可仅有恶堕值的角色，直接复用会将并未指定为性奴的角色纳入新系统；`IsSupportedVanillaStatus` 则是工作与面板可用性条件，不是 SSC 角色身份。

本轮建议统一范围为：具有训练组件且明确为 SSC 性奴身份的 Pawn，以及需要兼容修复的已有有效锁链对象。仅有特化、恶堕值、原版奴隶身份或组件本身不足以自动纳入。矛盾的身份/锁链数据先按既有关系修复流程核对，不将已明确离开性奴身份的人永久困在规则中。新系统不以 `TrainingMode.Enabled` 或研究完成为适用前提。

- 已指定性奴但尚未首次绑定的准备对象可初始化和配置；“仅限主人”在无有效主人时不能匹配任意人，R5 的指定候选准备例外只适用于调教，不给普通行为授予主人豁免。
- 暂不适用的 Pawn 可以保留历史配置；配置存在不表示正在受限。总开关关闭表示停止执行限制，也不表示角色尚未初始化。
- 实际主人关系应来自当前有效绑定，不以旧引用、销毁对象或 `GetResolvedMaster` 的调教员后备结果冒充；仅离图不等于绑定失效。本轮不重做主人死亡与复活玩法，但必须保证失效引用不授予豁免、不强行指派无效对象。
- 首次适用、运行判断、默认批量应用以及 UI 状态共享这一适用判定；UI 另外保留其正常可访问范围。未来新增无主玩法时再扩展具体身份流程，不在本轮通过默认分支实现。

### F3. 唯一指定调教员，保留现有资质过滤

证据：[TrainerAssignmentUtility](../../Sexslavecraft/common/TrainerAssignmentUtility.cs) `IsAllowedTrainer` 在旧例外或公交车状态下提前返回 `true`，不再检查 `selectedTrainer`；`GetForcedMaster`、[SSCBondUtility](../../Sexslavecraft/common/SSCBondUtility.cs) `TryAssignTrainer/Bind`、[读档修复](../../Sexslavecraft/Comps/Comp_Train.cs) 也分别使用这些状态。

已确认按 R18 采用唯一指定调教员：开放非主人调教只是允许改选符合现有资质的非主人，不代表所有合格人员都可以接替。选定 B 后，未选定的非主人 C 不得因该许可开启、旧例外或公交车状态而获得调教许可。因此不能把旧布尔字段机械替换成新开关，必须清理上述绕过 `selectedTrainer` 的分支。实际主人仍按 R4 保留固定豁免，不能被指定 B 排除；这不使其他人变成候补调教员。

资质过滤与对特定对象的指派许可分开处理。当前 `GetTrainerCandidates` 从同地图 `FreeColonists` 中筛选，`CanAssignAsTrainer` 排除死亡、倒地、缺少工作设置或未启用 `TrainSexSlave` 工作类型的候选。有主性奴继续沿用这些现有过滤及其上游工作资格条件，不借新限制系统扩大调教员身份范围；只替换旧例外、非主人许可与指定对象之间的关系判断。研究、预约、能力等正常执行条件继续保留。

**整体复盘后的边界建议：** 当前 `IsAllowedTrainer` 在没有强制主人且 `selectedTrainer == null` 时返回 `true`，这不符合唯一指定的目标，不能原样沿用。

- 没有指定者时，不自动给任意非主人分配工作；实际主人仍可通过 R4 发起有效请求。非主人许可关闭且已有有效主人时，按 R5 固定为主人；除此之外不自动挑选候补。指定对象倒地、暂时离图、关闭工作类型等，只影响当前可执行性，不立即抹去指派；死亡、销毁等失效引用则清理并显示原因。
- 唯一指定负责日常自动工作分配；实际主人豁免负责“主人发起时是否被 SSC 拒绝”。建议自动扫描优先且只分配给当前指定者，不因主人身份主动抢占指定者的工作；主人通过合法入口实际发起时，许可检查不得用“未被指定”拒绝。玩家命令和 AI 的实际许可一致，差异只在工作选择与已有排班逻辑，不新增玩家专属豁免。
- 系统总开关关闭时，非主人许可与强制主人锁定暂停，但已保存的唯一指派继续作为工作分配配置，不能退化为任何人都自动来做。重新开启后按保存的许可核对指派。研究、工作资格和仪式关系条件始终保留。
- 按 R5 强制改为主人后，重新允许非主人建议保留当前主人作为指定者，等待显式改选，不自动恢复一份隐藏的旧人选。这样不需要额外维护历史引用，也不会在重新开放许可时突然恢复过时指派。

许可、绑定、总开关或显式批量配置变化时，通过统一变更处理同步有效值、界面、指派与未开始任务；读档修复使用相同规则。**本轮公交车特化只覆盖普通被动项，所以单独切换该特化或特化强制开关不应改变调教许可或指定者。** 前文把它们列为调教许可变更来源的表述已撤回，不为尚未设计的其他特化预埋写值逻辑。

现有 `TrainingJobUtility.TryValidateStartOrAbort` 只检查目标能力，未复查指定调教者。应抽出纯许可检查供开始前复用，不能直接调用包含 `isBeingTrained`、冷却和预约的完整工作筛选，否则可能把本任务自己创建的占用判为失败。保留已有资质过滤还意味着区分“能被选择”和“此刻能执行”，不可把候选菜单的一次结果当作永久资格。

### F4. 仪式主持资格采用“绑定主人或当前选定调教者”

证据：`RitualRole_BindingSlave` 用旧例外跳过锁链与 `selectedTrainer` 一致性；`RitualRole_BindingMaster` 按 `selectedTrainer` 排除其他候选；[CorruptionProgressionUtility](../../Sexslavecraft/common/CorruptionProgressionUtility.cs) 调用 `SSCBondUtility.Bind`，其默认 `replaceExisting=false`。

选择非主人调教者后，真正主人可能在仪式候选阶段被排除。旧例外会使非主人进入某些仪式路径，但不能据此称为“自动改绑”：现有 `Bind` 默认拒绝覆盖已有主人。

已确认的处理规则是：对于确定的仪式目标，候选人是其实际绑定主人，或者是其当前选定调教者，即通过主持关系资格检查。两者为并列资格，不是由选定调教者替代主人。

- 主人 A、当前调教者 B 均有资格；未被选定的第三人 C 不因“允许非主人调教”开启而取得主持资格。
- 调教者从 B 更换为 C 后，B 不再凭旧指派取得资格，C 获得资格；A 始终保留资格。若 B 本身就是绑定主人，则仍凭主人身份具有资格。
- 清除调教者选择不影响已有绑定主人的主持资格；首次绑定前则可由当前选定调教者取得关系资格，仍须保留 F1 中的指定入口。
- 主持资格不赋予主奴绑定，也不授权替换已有主人；非主人主持不自动获得 R4 的全部行为豁免。

迁移时需同时调整主人角色与性奴角色的配对检查，不能只修改一侧。`RitualRole_BindingMaster` 当前还先要求 `IsMaster` 身份，应避免合法选定调教者通过新关系判定后又被旧身份门槛排除；认可其主持资格不需要把它改成主人身份或重做整个身份系统。这里调整的是 R11 的仪式主持关系资格，不是放宽 R18 保留的日常调教员候选资质过滤；不能通过仪式入口把不符合现有调教员资质的人写成选定调教者。能力、研究、可达性、预约等正常任务条件仍按既有流程检查。

主持关系资格按 R11；仪式执行阶段按 F2 归入独立调教类，既校验主持关系和正常仪式条件，也不再叠加普通主动/被动许可。

### F5. 主人放行必须在普通限制、装备限制之前统一判断

证据：[SSCSexInteractionPolicy](../../Sexslavecraft/common/SSCSexInteractionPolicy.cs) 在强制行为分支先检查发起者限制；开启 `allowSexSlaveRape` 后又先检查防护装备，只有另一分支才检查主人匹配。当前并没有独立的“主人最高优先放行”。

实施时应先依据 `SSCBondUtility.IsBoundTo(receiver, initiator)` 检查实际绑定，不能使用“具有主人身份”、`selectedTrainer` 或有后备调教者逻辑的 `GetResolvedMaster`。然后再进入非主人限制与装备判断。主人豁免必须在发起驱动、接收驱动和重新校验中得到一致结果。

**本次分析方案：保留装备对非主人强制行为的额外拦截，不新增装备开关。** `CompSSRapeCheck` 当前只是装备标记，实际策略在“允许强制行为”的分支中仍因该标记拒绝；因此其含义是“许可之外的装备防护”，不能从组件内“跳过链奴检查”的旧注释推导为放行。仓库中的 `Apparel_EFOutfit` 使用此标记。

- 在本系统适用范围内，普通强制行为须同时通过行为许可和接收方防护装备检查；穿戴标记装备时，非主人仍被拦截。实际主人按 R4 先放行。
- 公交车特化默认/强制仅决定许可项，不移除装备防护。旧公交车提前放行曾绕过装备，新系统不复刻该旁路；这一变化须写入迁移说明与物品/规则提示。
- 该标记不扩展为单人自慰、普通非强制行为、独立调教或绑定仪式的禁用条件。其他 RJW 能力及装备物理可行性仍由其正常流程检查，不混入这项 SSC 标记规则。
- 总开关关闭时，该项 SSC 额外拦截也暂停；装备自身属性和其他模组判断不受影响。穿脱装备不覆盖个体保存值，只使有效判断及原因提示更新，开始前应复核。

### F6. 公交车仅覆盖两项被动许可，落实其生效事件

证据：[Comp_Train](../../Sexslavecraft/Comps/Comp_Train.cs) `ReconcileSpecialization` 明确保留终极 Hediff；`DetectAdoptableType` 按既定顺序认领状态。[特化设置](../../Sexslavecraft/Comps/Comp_Train.Specialization.cs) 在 `SetSpecialization` 中直接写旧许可，重复选择同一方向也会写入。

**本次分析方案：当前方向为公交车，或具有整理后的有效基础/终极公交车状态时，两项被动覆盖适用。** 同时仍须属于第 2.3 节的新限制系统适用对象。理由是：`SetSpecialization(Bus)` 立即确定方向，而基础 Hediff 可能等到 `ReconcileSpecialization` 才补齐，不应形成短暂的规则空窗；终极公交车状态按现有代码保留，切换其他方向不应使其已有被动特例消失。只有历史进度、已存人格物品中的特化或其他角色的公交车状态，不构成当前角色适用条件。

方向切换、Hediff 增删和人格/克隆恢复应在状态整理完成后统一通知规则系统，避免处理中短暂出现旧方向、残留基础状态或空状态时错误写默认。当前方向已不是公交车且基础与终极状态均不存在时，停止其强制覆盖。终极状态仍在则继续覆盖。移除基础 Hediff 但保留公交车方向时，现有代码会重建基础状态，不能将这一短暂缺失视为失去特化。

实际强制条件为：**系统总开关开启 ＋ 全局特化强制开关开启 ＋ 当前角色适用公交车规则**。三者满足时，只有文件声明的两项被动许可有效值为允许；缺少任一条件就不执行该强制层。保持 R4 主人固定豁免及 F5 的额外装备检查。旧 `IsBusSpecialized/HasAnyBusState` 对整次行为的提前返回必须清理，不能与这套条目覆盖并存。

**默认只在明确事件写入，不跟随强制开关反复写入。** 建议为当前 Pawn 保存一个“公交车默认已处理”的元数据标记：它不是行为选项，也不是每个特化的一套配置，仅防止认领、往返切换和恢复流程重置玩家选择；随 F7 的个体配置保留，新克隆不继承来源标记。本轮只有公交车需要此标记，不预建所有特化的配置管理系统。

| 事件 | 个体原值与默认写入 | 强制层 |
| --- | --- | --- |
| 新角色首次初始化且已适用公交车 | 先复制普通默认，再将两项被动许可设为文件默认值，标记已处理；不因全局强制当前关闭而跳过默认。 | 按两个全局开关及当前状态解析。 |
| 已初始化角色首次真正取得公交车，且默认尚未处理 | 仅将两项被动许可设为文件默认值并标记；其余规则不变。这是一次明确的特化取得事件，不是普通全局默认变更。 | 全局强制开启时覆盖两项，否则允许之后个体编辑。 |
| 重复选择、基础升为终极、周期认领或重新读档 | 不再次写默认；已有配置与标记保留。 | 读取当前最终状态。 |
| 失去全部公交车适用条件 | 保留个体保存值及已处理标记，不自动写回普通默认，也不恢复取得特化之前的隐藏副本。 | 停止公交车覆盖。若此前默认已写为允许，它仍是保存选择；失去强制不等于自动禁止。 |

| 切换方向但保留终极公交车 | 不写默认、不修改其他规则。 | 继续适用两项公交车覆盖。 |
| 关闭/开启全局特化强制或系统总开关 | 不改个体原值、不清标记。 | 后续判断立即按全局状态暂停/恢复；当前阶段按 F8 收尾。 |
| 显式“为所有性奴应用默认配置” | 当前适用公交车的角色无论标记如何，均重设普通默认并恢复这两项特化默认，标记已处理；当前不适用公交车则只按普通默认重设，不清已有特化处理历史。 | 按当前全局开关解析，不重置开关。 |
| 旧角色升级迁移 | 先一次性映射旧选择；当前适用公交车的对象记为已处理，避免随后认领又覆盖迁移结果。未适用且未处理者在未来首次取得时走取得事件。 | 当前适用者按文件强制值与全局开关解析。 |
| 人格植入到已有配置的 Pawn | 按 F7 保留接收方原值；恢复后若适用公交车则标记已处理，不借恢复事件改写两项。未初始化接收者走首次初始化。 | 按恢复后的状态解析，不继承人格来源的设置。 |
| 新克隆 | 清除复制来的个体配置与默认处理标记，首次适用时初始化；成熟及重复状态同步不再次写默认。 | 按克隆自身状态和全局开关解析。 |

默认值写入与“默认已处理”标记应一起成功保存；失败不得仅留下完成标记。标记缺失的已配置旧数据按迁移流程补齐，不能在普通查询时反复猜测是否需要覆盖。本方案允许玩家通过手动编辑或显式批量恢复重设保存值，不利用反复切换特化强制重置；切换非公交车方向也不再沿用旧代码把整组许可关闭。

### F7. 配置归属与人格、克隆、身份和绑定的生命周期

证据：[Settings](../../Sexslavecraft/common/Settings.cs) 保存全局设置；`Comp_Train.PostExposeData` 保存个体数据；`Comp_Train.Specialization.SetSpecialization/RestoreSpecializationProgress` 重设旧许可；[ExcretionUtility](../../Sexslavecraft/common/ExcretionUtility.cs) 在人格植入时恢复方向；[RabbitCloneUtility](../../Sexslavecraft/common/RabbitCloneUtility.cs) 为克隆复制旧许可。

升级迁移按 R14 执行：全局设置和每个旧角色在首次接入新系统时复制初始化，之后使用已保存的新配置。建议独立记录初始化完成状态或迁移版本，区分旧字段缺失和明确的 `false`，确保重复读档不会重新导入旧值或覆盖玩家后续修改。

**整体复盘补充：迁移要保存输入与来源，不能仅判断“新字段不存在”。**

- 区分旧存档中原本适用但待迁移的角色、新系统创建但尚未首次适用的角色、已有配置的角色。建议保存当前存档的配置版本并明确待迁移对象；旧存档里原本普通、直到升级后才首次适用的角色按 R15 取新默认，不能永远被当作旧角色读取遗留字段。
- 在旧修复、`SetSpecialization` 和状态认领写字段之前捕获迁移所需的旧值。当前 `Comp_Train.PostExposeData/PostLoadInit` 已会改指定调教员，`CompTickRare/ReconcileSpecialization` 可能间接改旧例外；这些写入之后再迁移会丢失玩家旧选择。先读原始输入，等引用恢复及必要关系核对完成后生成新配置，再执行使用新规则的修复。
- 全局旧设置属于模组设置文件，可能被升级或其他存档使用后改动；当前存档开始迁移时应固定其可用旧设置快照，不让同一存档的地图角色与稍后载入的世界角色各取不同时间的设置。若历史上该存档使用的全局值已不可获得，明确使用升级时可获得的旧设置，不声称能恢复不存在的历史记录。
- 全局默认迁移、每个 Pawn 的个体迁移及显式批量默认是不同操作；批量恢复完成的新配置优先，后续不能再被未清理的迁移队列覆盖。待迁移旧角色未处理完之前，应保留必要兼容读取，不能为了清理代码提前丢掉来源。
- 新字段未来增加时按配置版本补缺项，保留已存在的值；补一项不等于重新复制整份全局默认。已初始化标记和数据结构实际完整性应分别校验。

新角色按 R15 在首次能够使用或受该机制影响时初始化，必须在第一次实际限制判断之前完成，不能依赖玩家先打开界面。建议保存明确的“已初始化”标记，不能用某项值恰好为 `false` 代替。已经初始化的角色在重复检查、打开面板、读档时均不得再次从全局默认复制；在角色生成后、首次适用前修改全局默认，应使用其首次适用时的最新默认。

R17 是用户显式要求的配置重设，不应通过清除迁移标记来实现。批量应用后保留或补齐初始化完成状态，避免下次检查又导入旧配置。系统总开关重新开启时也应同步有效调教许可与调教者状态，不能依赖再次打开界面才恢复限制。

读档后特化认领、人格植入、克隆生成、身份或绑定关系变化属于新配置的后续生命周期，仍需按各自规则处理，不应每次都重新触发旧版本迁移。

**本次分析方案：个体限制属于玩家对当前 Pawn 的管理配置，随该 Pawn 保存，不随人格物品转移，也不与克隆来源持续同步。** 理由是这些选项表达玩家如何管理当前角色，而不是人格的记忆或成长；它也与 R15“新角色首次适用时采用当时默认值”一致。人格携带的身份、特化及现有绑定恢复机制仍沿用现行功能，恢复后的状态参与有效规则解析，但不因此复制另一角色的限制选择。

需要分开保存三类角色数据：个体规则原值、初始化/配置版本及公交车默认处理标记、绑定与指定调教员等关系数据。特化强制后的有效值和主人豁免属于根据当前状态计算的结果，不能当作原始选择复制或永久写回。系统总开关和特化强制开关均保存在 Mod 总设置中，不属于任何人格或角色快照。

| 事件 | 个体配置处理 | 关系与有效规则处理 |
| --- | --- | --- |
| 人格提取、生成物品或留下空壳 | 原 Pawn 保留自己的配置及初始化标记；人格物品不携带这套管理配置。 | 按提取后的实际身份、绑定和特化重新判断适用范围，不因为配置仍存在就强行启动限制。 |
| 人格植入 | 接收 Pawn 已初始化则保留其原配置；从未初始化则在植入完成且首次适用时按 R15 初始化。旧人格物品缺少新配置无需补造人格侧数据。 | 沿用现行身份、特化和绑定恢复；全部恢复结束后重新解析有效值，校验调教员关系。绑定恢复失败不凭物品中的主人引用授予豁免。 |

**代码接入中必须补齐的边界：**

- [人格存储组件](../../Sexslavecraft/Comps/ThingsComp_PE_PES.cs) 的 `StorePawnData` 保存身份、特化等快照，当前未直接保存旧许可或指定调教员。新配置不应顺手加入人格快照或其复制逻辑；也不应在植入时用物品缺省值覆盖接收 Pawn 已有配置。
- `ExcretionUtility.InheritEverything` 先调用 `CleanConsumerData` 解绑并暂设未指定身份，再恢复成长、特化、身份、绑定，最后恢复特化状态并执行 `ReconcileSpecialization`。应将新规则的初始化、特化变更处理与调教员校验推迟至完整恢复结束，防止中间状态触发默认重置或错误锁定。保留原配置不等于该恢复流程已经具备事务回滚；现有异常路径也需刷新为实际留下的状态，不能继续使用旧主人或旧特化的缓存结论。
- `RestoreSpecializationProgress` 会调用 `SetSpecialization`，后者现会写旧例外。迁移时应移除这些旧写入对新配置的影响。人格恢复、读档认领和身份往返均不是“为所有性奴应用默认配置”；特化强制层按全局开关与最终状态重新解析，首次真正取得特化等默认写入事件严格按 F6 表处理，已有配置的人格恢复不改写默认。
- `RabbitCloneUtility.TryCreateRabbitClone` 先用 `Find.PawnDuplicator.Duplicate(source)` 复制整个 Pawn，`PrepareFreshRabbitCloneBody` 又显式复制旧许可和调教员。因此仅删除旧字段赋值不够，还要防止新增配置对象、初始化标记或缓存被复制后误认为已独立初始化。为新克隆创建独立配置容器，初始化前完成必要的身份与特化整理；成熟或后续状态同步不得再从来源覆盖个体选择。此处理仅针对新克隆创建路径，不用于普通读档。
- `SSCIdentityUtility.TrySetIdentity` 离开性奴身份时清理仪式、关闭调教并清空指定者；这与保留限制偏好并不冲突。`SSCBondUtility.Unbind` 默认只在指定者为旧主人或没有旧主人时清空，已有第三方指定者可能保留；应复核其当前资格，不将所有解绑都改成恢复默认，也不把残留指定者当作已绑定主人。指定者无效后的空选择规则仍见 F3，不自动开放给所有人。
- 关系或身份发生变化时，使旧许可缓存失效，并在尚未开始任务的下一次检查中使用最新关系；进行中任务按统一生命周期策略收尾。重新绑定不会重新导入迁移字段，也不能借身份往返规避玩家已保存的限制。

本方案不扩大无主性奴玩法；解绑后哪些规则适用仍取决于本轮适用范围，不能从“保留配置”推导出新增身份功能。R17 的显式批量应用依然可以重设当前适用角色，处于不适用状态的角色保留原配置。

主人最高放行、独立调教许可及废弃整个行为的公交车豁免，可能与旧复合行为不同。迁移目标应是保留能够明确映射的选择，并记录新规则有意改变的部分，不能承诺所有旧场景逐项完全相同。

### F8. 单人行为的识别和读档收尾需要专门覆盖

证据：[Harmony_ProtectSexSlave](../../Sexslavecraft/ThePatches/Harmony_ProtectSexSlave.cs) `DetermineRoles/NextToil_Prefix/Start_Postfix`。本机 RJW 的 `JobGiver_Masturbate` 与右键入口把自身填为目标，`JobDriver_Masturbate` 继承发起驱动、独立覆盖预约，并通过 `Start/End` 执行单人流程。

当前没有单人分支，会对自己执行主人匹配。新分类应优先识别已知单人任务及可靠的场景信息；不能把所有空目标等同于自慰，也不能因为缺少第二人就跳过已知单人限制。

内存中的已开始标记不随存档保存；现有恢复逻辑依赖接收驱动及参与者列表，不能覆盖单人自慰。需要可靠地区分读档后的准备中、已开始和收尾，避免把预先创建的 `SexProps` 当成开始证明，也避免已经开始的单人行为被重新拒绝。

仪式准备步骤已经创建 `SexProps` 和接收任务，而实际 `Start` 在下一步骤；本机 RJW 接收任务初始化会提前登记参与者。若从这一准备状态恢复，现有推断可能误认为已开始，直到 `Start` 才兜底拒绝。仪式自身已有保存的 `phaseSceneStarted` 标记，可作为统一生命周期适配时的依据；应增加准备完成但未开始的恢复测试，而非只测试正常双人收尾。该路径为静态时序发现，尚未游戏内复现。

日常调教在移动前设置 `isBeingTrained=true`，清理主要挂在行为步骤的结束回调。走位后被新许可拒绝时，应明确清理本次准备占用，不发收益、不影响别人的场景；当前后续工作扫描虽有残留修复，也不能把它当成新系统拒绝流程的唯一保证。

**“已开始可正常收尾”的范围需要限制到当前场景实例。** 建议上下文至少关联发起任务、接收任务、参与者与用途；仪式另包含阶段。某人正在接收其他场景、上一阶段已经开始或旧任务曾成功，均不能让新加入者、新阶段或复用驱动的后续请求免检。每个新阶段开始前重新取当前配置，已开始的当前阶段保持正常收尾；新加入者按自己的发起方向重新检查。

允许结果不能长期缓存为后续阶段通行证。总开关、批量配置、关系、装备或指定者变化只影响后续尚未开始的请求；正常失效、死亡、离图等任务自身终止条件仍由原生命周期执行，不因“允许收尾”强留任务。清理、收益和开始消息应按场景/阶段防重复，并验证晚到回调不会清理新的任务。旧存档缺少新生命周期标记时要结合可验证的任务进度恢复，不能一律按未开始拒绝或一律按已开始放行。

### F9. 角色适配、玩家指派和兼容白名单仍有旁路

证据：`Harmony_ProtectSexSlave.DetermineRoles` 在场景数据未就绪时读取 `targetA.Thing as Pawn`，而本机 RJW 的 `JobDriver_Sex.Partner` 还支持 `PartnerPawn` 和尸体中的 Pawn。空角色路径会跳过全部策略，可能漏掉发起方本身的限制。

应使用经核对的 RJW 角色信息，避免只支持一种目标布局；无法确认目标时仍区分已知发起方限制与需要对象的限制。此处是已有任务适配完整性，不要求本轮新增对象种类的玩法选项。

预约阶段还保留 `playerForced` 放行，按 R3 应移除其保护豁免含义；但不能把所有名为 `forced` 的参数一并删除，部分用于预约、工作优先级或失败日志，且 SSC 仪式也会自行设置该标记。

日常调教的手动指派目前可以越过排班时段，属于已有调度规则。R3 要求新限制许可一致，不意味着本轮顺带取消手动立即执行工作的调度能力。

**LifeForce 白名单：本轮方案为先适配，再取消无条件放行。** `KnownDirectAllowJobs` 包含 `rjw_genes_lifeforce_randomrape` 与 `rjw_genes_lifeforce_seduced`。本次核对本机整合包的 `Jobs_LifeForce.xml`，前者使用 RJW `JobDriver_RandomRape`，后者使用 `RJW_Genes.JobDriver_Seduced`。它们是需要正确识别角色和用途的兼容入口，任务名称本身不应成为跳过所有限制的权限。

- `randomrape` 按普通强制行为适配；`seduced` 需核对其驱动、关联任务与实际 `SexProps`，不能仅凭名称将当前 pawn 当发起者或一律归入非强制。此次仅核对后者的 JobDef，尚未验证其驱动内部时序，因此不宣称该适配已完成。
- 涉及适用角色时使用同一主人豁免、普通许可和装备规则；不涉及适用角色时不增加 SSC 限制。特殊基因或精神状态不自动取得整次行为放行，也不归入独立调教。
- 按完整入口组验证角色还原、预约、开始、接收与清理后再删除相应白名单项，遵守 R6 的迁移顺序；不能先删白名单却让未知角色路径继续隐式放行。未完成适配时应保留明确的兼容缺口记录，不能标记这一组已接管。
- [LifeForceConflictUtility](../../Sexslavecraft/common/LifeForceConflictUtility.cs) 的基因冲突处理另属既有功能，本轮不顺带重做。它只在部分目标校验入口调用，且会修改角色、生成物品，不能用来代替权限判断，也不能在纯规则查询中调用或假定所有白名单任务此前都已被它排除。

**原版 Lovin：本轮纳入普通双人非强制行为的覆盖范围，不新增专属开关。** 本次复核本机 RJW `1.6/Source/Harmony/patch_lovin.cs`：`override_lovin=true` 时把原版 `JobDriver_Lovin` 转为 RJW 任务；关闭时原版驱动不进入 RJW 基类拦截，必须另补适配。

- 以实际产生行为的发起任务及其 `Partner` 建立方向，并在关联任务与读档恢复中保持一致；实施前须核对原版目标版本是否存在双方各自持有 Lovin 任务等情况。不能按性别、姿势、主人身份猜方向，也不能将同一场景在接收端反转成第二次主动请求，从而误用主动限制。
- 替换开启时最终由 RJW 路径接管，原版适配不另建重复的场景或结算；替换关闭时，在任务生成/准备阶段及真正开始前检查统一策略。两种设置都验证主人发起与反向行为，以及双方都是适用角色的情形。
- 本机 RJW 还在 `JobDriver.Cleanup` 的 `Succeeded` 分支处理原版 Lovin 的结算。拒绝或取消必须保持失败/中止语义，不能为清理方便标记成功，否则可能产生没有实际完成行为的结算；不应全局禁用 RJW 的正常 Cleanup。
- 现有进行中任务读档按统一生命周期规则收尾。第三方独立 Lovin 驱动不因名称相似而自动宣布兼容，需逐项适配；本轮明确覆盖原版驱动与已支持的 RJW 路径。

### F10. 新限制还需接入产生任务之前的副作用

证据：[Harmony_BusTrade](../../Sexslavecraft/ThePatches/Harmony_BusTrade.cs) 在下达性行为任务前终止原任务、插入等待并显示发生消息；Pawn 交易路径末尾增加特化进度，并不依赖场景完成。[DogSpecializationUtility](../../Sexslavecraft/common/DogSpecializationUtility.cs) 先消耗事件掷骰冷却，再尝试启动任务。

**本次分析方案：保留既有交易进度为交易本身的收益，把后续任务、开始消息与行为结算分开。** 依据是现有 `TradeDeal.TryExecute` 后置补丁已要求交易成功且确实成交；派系分支不创建行为任务也增加进度，Pawn 商人分支即使抽到不发生行为的结果仍会增加。因此将全部收益改为“行为完成才奖励”会额外改变特化成长，本轮不这样处理。

| 层次 | 本轮处理 |
| --- | --- |
| 实际交易 | 已完成的交易不因后续行为被限制而撤回；保留现有分支、收益公式、终极状态判断及飞船交易不触发的范围，不顺带调整数值平衡。 |
| 交易成长 | 在满足现有交易成长条件时按一次交易事件结算一次；后续行为被拒绝、距离不符或未能开始，不取消交易本身收益。保持交易分支的既有检查条件，不把所有未通过前置条件的交易统一新增奖励。 |
| 后续行为尝试 | 保留现有掷骰概率和发起方向。抽到自愿分支时是交易角色发起，应检查其主动许可；对方发起的强制分支则检查相应方向。公交车的被动特化规则不替代自身主动许可。被规则拒绝不重掷、不改抽其他分支。 |
| 任务调度 | 同图、距离、能力、JobDef 与新许可等预检均在 `StopAll`、等待任务和下达行为任务之前完成；正式开始前再次检查。预检拒绝不打断任何角色当前工作。 |
| 已接受任务但后来失败 | 任务下达成功不等于行为已开始。若准备期间条件变化，按本次任务的关联关系清理预约、等待与接收状态，不通过 `StopAll` 终止角色后来接到的无关工作。 |
| 行为成长与结算 | 仍由实际行为的正常结算入口触发，不能在交易回调中模拟成功或补发。[BusSpecializationUtility](../../Sexslavecraft/common/BusSpecializationUtility.cs) 的行为成长与交易成长是两个来源；本轮保留两者，避免在新入口或重复回调中再次发放同一来源。 |

**消息方案：** “发生了行为”的消息仅在确认真正开始后显示一次；后续完成收益仍按正常结算处理。被规则挡住的交易后续事件可显示一次中性说明，例如“交易已完成，后续行为因限制未开始”，不能显示为已经发生，也不能冒充掷骰抽到的原谅分支。手动指派在可用的失败原因提示中显示具体限制；高频自主 AI 筛选不反复弹消息，只保留受控调试日志。同一事件在预约、开始和接收端多次拒绝应合并提示。

狗特化的既有事件冷却按掷骰消耗，保留这一语义；调度后续任务前接入同一预检，被拒绝不退还掷骰冷却，不撤回先前已满足条件的工作成长，也不产生未发生行为的结算。此处只统一事件阶段和副作用时序，不新增特化许可或改变该事件玩法。

### F11. 调教 ITab 左侧可展开子窗口与规则状态同步

证据：[ITab_SexSlaveTraining](../../Sexslavecraft/ITab/ITab_SexSlaveTraining.cs) 的设置区受性奴身份和基础调教研究控制，面板采用固定分区高度；全局设置在 `Settings.DoSettingsWindowContents` 中直接绘制。旧“允许其他人”位于调教区。

已确认：个体限制控制采用现有调教 ITab 左侧可展开的附属子窗口。展开后在子窗口内组织“主动发起”“被动接受”“调教”三类设置，收起时隐藏限制控制内容。“允许接受非主人调教”移至调教类；全局默认调整区采用相同分类。此位置方案不再待定；各项及特化强制开关的具体布局另行安排。

**本次分析采用的首版方案如下，尺寸是实现起点，最终以游戏内测试调整。**

| 项目 | 首版方案 | 依据与边界 |
| --- | --- | --- |
| 尺寸 | 左侧限制面板宽 `320`、目标高度 `560`，与现有 `360 × 560` 主面板等高，间隔 `8`；正常展开总宽 `688`。均使用游戏 UI 逻辑坐标。 | 与现有面板高度对齐；长说明换行或放提示，不靠不断扩大宽度容纳。实际高度按可用区域收缩。 |
| 承载方式 | 优先在同一 ITab 宿主中扩展总绘制区域，视觉上左侧为附属子窗口、右侧为原调教面板；两区各自绘制背景并独立滚动。 | 单一宿主便于统一目标、关闭和输入；主面板内部宽度与布局保持原样。先验证 ITab 动态尺寸能否正确刷新外框和命中区域，不能仅在原 `360` 宽区域之外使用负坐标绘制。 |
| 展开入口 | 在主面板的固定顶部操作区提供“行为限制”展开/收起按钮，放在内容滚动区和研究锁定分支之外。 | 不要求用户先滚到底部，也不因未完成研究而失去配置入口；增加固定区后同步扣除主滚动区可用高度。 |
| 初始状态与记忆 | 新游戏会话或载入存档时默认收起；同一会话中记住最后一次展开选择，切换角色或关闭后重新打开 ITab 沿用该选择。 | 仅保存为当前游戏会话的 UI 状态，不写入 Pawn 或规则存档；切换存档重置，避免共享 ITab 实例泄漏上一局状态。 |
| 滚动状态 | 左右独立滚动；切换目标时左侧回到顶部，同一目标临时收起再展开可保留位置。 | 避免新目标打开时停在上一人的中段，也避免左侧滚轮同时推动主面板或地图。 |
| 研究门槛 | 已适用新限制系统的角色，研究未完成时仍可查看、编辑限制，包括调教规则。 | 配置许可不等于解锁工作；主面板调教执行及其研究条件仍按现有规则。新系统保护不应早于设置访问生效而无法调整。 |
| 当前不适用 | 展示不适用原因，已有保存配置可只读查看；不提供正常编辑，不因打开窗口创建新配置。 | 配置保留与当前生效分开。正常角色首次初始化仍由 R15 的适用条件触发；总开关关闭则按既定方案允许编辑适用角色配置，并显示全局暂停状态。 |

**屏幕边缘适配：** 以当前 UI 缩放下的可用区域计算整体外框，扣除检查器等实际占用区域，边缘目标留白 `12`。正常情况下保证限制面板在主面板左侧；左边不足时移动或扩展整个组合面板，不把子窗口单独甩到右侧。展开时主面板的屏幕位置允许随组合外框调整，但其内部布局与滚动状态应保持。高度不足时缩短两区可视高度，以垂直滚动承载内容，不缩小文字。

若可用宽度不足以容纳 `688`，首版采用紧凑回退：同一宿主暂时只显示限制面板，保留固定的“返回调教”入口，避免相互覆盖或挤窄至无法操作。正常宽度仍为左侧并排形式；分辨率或 UI 缩放变化后重新计算布局，回退不改变展开偏好或规则值。实际外框锚点、可用高度与窗口遮挡需在游戏中确认，不把上述逻辑坐标直接当作物理像素。

**目标与规则状态同步：**

- 子窗口与当前 ITab 的单一目标保持一致，标题显示角色名称；关闭 ITab、离开可用选择或目标失效时停止显示和编辑，不保留悬浮窗口。多选时不新增批量编辑语义，沿用宿主目标解析；无法确定唯一目标则显示提示并禁用编辑。
- 切换目标后重读配置；已打开的下拉菜单、延迟回调等必须校验创建时的目标仍有效，不能通过回调中的当前 `SelPawn` 将操作写到新选中的角色。
- 每项显示个体保存值、特化强制后的有效值与文件规则来源，以及主人固定豁免的适用范围；不提供“持续继承全局”状态。角色窗口不提供特化强制开关，只提示其 Mod 全局状态；全局切换后应立即刷新受影响项及禁用原因，底层选择不变。非主人调教许可变化后，主面板的调教者选择控件同步反映有效值，不能只读取原始布尔字段。
- 展开、收起、滚动和切换角色不改写限制选择；配置修改通过统一入口生效，左右面板不各自维护一份规则数据。纯 UI 展开记忆与个体配置初始化标记完全分开。

**基本实现后必须游戏内测试：** 静态代码与布局计算无法验证 RimWorld 的实际 ITab 锚点、外框更新、缩放、窗口层级和鼠标事件。先按上述方案完成可交互版本，再记录问题并调整尺寸、留白或宿主承载方式；不能仅凭编译通过认定子窗口完成。

| 游戏内测试组 | 重点观察 |
| --- | --- |
| 分辨率与缩放 | 至少覆盖 `1280 × 720`、`1920 × 1080` 及实际支持的较大 UI 缩放；组合面板碰到左右边缘和高度不足时仍可访问全部条目，紧凑回退有返回入口。 |
| 展开与输入 | 展开/收起后外框、背景和命中范围一致；按钮无穿透；左右滚动互不干扰，不误触地图；下拉菜单与提示不被裁剪或挡住。 |
| 目标与会话 | 快速切换角色、打开菜单后切换目标、关闭/重开 ITab、取消选择、切地图和载入另一存档，不串写角色、不残留窗口；展开记忆符合上述范围。 |
| 规则访问 | 研究前后均可编辑适用角色的限制，但研究未完成不能执行调教；总开关关闭、特化强制、身份失效等状态的提示与可编辑性准确，调教员控件同步。 |
| 文本与内容 | 简中、繁中、英文、俄文标签和拒绝原因不溢出；长名字、长提示及最低可用高度下仍能滚动到最后一项。 |

全局设置窗口当前没有滚动容器；若大量追加默认项，需要重新安排布局或滚动区域，避免后面的设置无法访问。系统总开关与“是否启用特化强制规则”均放在 Mod 总设置的运行控制区，和行为规则默认编辑区分开；默认编辑区提供 R17 的批量应用操作。具体特化条目与覆盖值读取 Mod 文件，不在界面中另设每个特化的配置表。总开关关闭时仍可编辑与保存配置，界面显示限制暂停状态，特化强制项不得显示为正在执行；全局开关变化还应使相关有效值缓存失效。

简中、繁中、英文、俄文的运行时语言文件以及仓库内嵌语言副本需要清点。新拒绝原因不能继续全部显示“该性奴已经和别人链接过”；高频 AI 拒绝需要避免刷屏。
