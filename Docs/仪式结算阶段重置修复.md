# 仪式结算阶段重置修复

日期：2026-09-12。

## 根因与调用链

绑定仪式完整结束后，`RitualOutcomeEffectWorker_SSCBinding.Apply` 调用
`ConditioningUtility.ExecuteRitualOutcome`。新、旧评分分支都会先增加恶堕，再调用
`CorruptionProgressionUtility.ProcessCorruptionProgression(..., true, ...)`。
日常调教也使用这一阶段入口，但传入 `false`，不增加仪式专属锁链进度。

两个错误叠加导致仪式后阶段清零：

1. 仪式原先在恶堕 ≥30% / ≥50% 时直接给锁链加 20% / 30%，没有限制新进度必须由当前恶堕支持。
2. 随后的 `Need_Corruption.NeedInterval` 在恶堕低于阶段底线时，用“严重度减 0.1，再分段取值”的方式回退；分支仅覆盖 0.1～0.5，剩余情况统一赋值 0。高阶段通常会落入清零分支。

可复现例子：锁链 0.8、恶堕 0.65，在阶段结算时锁链增加至 1.1；下一次需求刷新发现恶堕不足 0.9，计算得到 1.0 后落入兜底分支，锁链被设为 0。

数值更正：早先的说明和测试宿主假设锁链最大严重度为 1.0。进一步核对本机游戏 `HediffDef` 构造器后确认，默认 `maxSeverity` 为 `float.MaxValue`，当前锁链 XML 也没有覆盖该值。因此旧实现这里实际到达 1.1，并不会自动钳制为 1.0。此差异不影响清零根因；测试宿主已改为读取 XML，并使用游戏默认值。

锁链是当前玩法阶段的依据，见 `SSCIdentityUtility.GetSexSlaveStage`；性奴 Trait 按历史最高恶堕同步，两者不能混为一谈。`SSCBondUtility.Bind` 及锁链 `AddToPawn` 会复用已有锁链，没有在重新绑定时清零严重度。

### 三种状态的区别

| 状态 | 数据来源 | 作用 |
|---|---|---|
| 当前恶堕率 | `Need_Corruption.CurLevel` | 仪式增量资格、自然衰减、装备维持等判断使用的当前值 |
| 当前性奴化玩法阶段 | `Hediff_ChainOfSexSlave.Severity` | 由锁链严重度对应 0.1 / 0.3 / 0.5 / 0.9 阶段，供身份工具和玩法门槛使用 |
| 历史恶堕 Trait | `HighestCorruptionLevel` 对应的 Trait 等级 | 记录历史里程碑，不等同于当前锁链进度 |

所以“当前恶堕下降”“锁链退阶”和“历史 Trait 等级变化”是不同操作。本次直接清零的是锁链严重度；绑定对象本身仍可能存在，但玩法阶段查询会返回 0。

### 为什么看起来在仪式结束时立即重置

仪式先发放恶堕收益，再执行共享阶段入口；下表中的 65% 指到达锁链成长结算时的值，已经包含之前发生的收益。

| 执行步骤 | 旧代码结果 |
|---|---|
| 进入锁链成长结算 | 锁链 0.8，恶堕 0.65；锁链当前位于 0.5 档 |
| 恶堕 ≥0.5，给锁链加 0.3 | 0.8 + 0.3 = 1.1；当前 XML 没有 1.0 严重度上限 |
| 新锁链阶段 | 位于 0.9 档，要求当前恶堕至少达到 0.9 |
| 后续需求刷新 | 扣除很小的自然衰减，恶堕仍约 0.65，低于 0.9，进入回退分支 |
| 旧回退先减 0.1 | 临时结果约为 1.0 |
| 仅匹配两个低区间 | 1.0 既不在 `[0.3, 0.5)`，也不在 `[0.1, 0.3)`，落入 `else` |
| 执行兜底赋值 | 锁链严重度变成 0，玩法阶段返回 0 |
| 最后的恶堕钳制 | 阶段 0 对应刹车上限 0.12，当前恶堕也可能随之被压到 12% |

旧分支的关键代码是：

```csharp
float newSev = chainSev - 0.1f;
if (newSev >= 0.3f && newSev < 0.5f) newSev = 0.3f;
else if (newSev >= 0.1f && newSev < 0.3f) newSev = 0.1f;
else newSev = 0f;
chainHediff.Severity = newSev;
```

最后的 `else` 把“高于所有已覆盖区间”也解释成了“低于第一阶段”。因此，即使没有刚完成仪式，已有高阶段锁链在自然衰减后进入这一分支，也可能直接清零。仪式越级成长只是特别容易制造这种数值组合。

此外，阶段阈值间隔不相等：0.1 到 0.3 相差 0.2，而 0.5 到 0.9 相差 0.4。固定减 0.1 本身就不等于退一级；例如锁链 0.4 减到 0.3，仍留在原来的阶段。

## 修改

- `CorruptionProgressionUtility`：仪式增量为原增量与 `max(0, 当前恶堕 - 已有严重度)` 中的较小值，防止跨入尚未达到的阶段，同时不降低已有进度。首次绑定的初始严重度仍为 0.2。
- `TrainingOutcomeUtility`：按锁链 HediffDef 的实际阶段表获取前一级底线，继续复用已有阈值兜底机制。
- `Need_Corruption`：自然回退使用前一级阶段底线，正常阶段链为 0.9 → 0.5 → 0.3 → 0.1 → 0。每次需求刷新最多退一级。
- 已解锁的装备/健康状态恶堕底线在回退判断前生效，避免维持装置在恰好达到阶段门槛时仍误退阶。
- 基础衰减为 0 时不再回退，与关闭自然衰减保持一致。旧评分仍保留原先不自然衰减的行为。

### 修复后的计算与边界

仪式增量使用：

```text
预算 = 当前恶堕 < 0.5 ? 0.2 : 0.3       // 仅在当前恶堕 ≥ 0.3 时执行
可新增空间 = max(0, 当前恶堕 - 已有严重度)
实际增量 = min(预算, 可新增空间)
```

例如：锁链 0.8、恶堕 0.65 时，可新增空间为 0，锁链保留 0.8；锁链 0.4、恶堕 0.5 时，增量为 0.1，锁链变为 0.5。限制作用于增量，因此不会直接把已有高进度压低到当前恶堕。

自然刷新则按“扣除自然衰减 → 应用已解锁的装备/健康底线 → 判断是否低于阶段底线 → 必要时退一级 → 重新按新阶段钳制恶堕”的顺序执行。

这次修复明确了两项规则：

- 仪式预算现在表示“最多增加 20% / 30%”，实际可能更少或为 0。
- 自然回退现在按阶段退一级，而不是固定减 0.1。因此部分低阶段原先只减少进度、仍留在本阶段的表现，也会改变。

修复不保证阶段永不降低。没有维持保护、恶堕确实低于阶段门槛且实际衰减为正时，仍会正常退阶；刚好踩在门槛上的数值也可能在下一轮自然扣减后退一级。

## 其余审查发现

这次修复聚焦阶段清零。仪式结算另外存在两处独立问题，尚未改动：

- `IsRitualCompletedSuccessfully` 是所有仪式共用的静态布尔值，没有绑定到具体 `LordJob_Ritual`。存在并行仪式或异常结算遗留标记相互影响的风险；尚未在游戏中复现。
- `ProcessRitualCorruptionProgression` 接收 `changes` 但不添加锁链成长说明，因此信件中的“未触发新的阶段”不一定准确反映实际锁链升级。

## 存档

未新增存档字段。修复可阻止之后发生的错误清零，但已有锁链严重度没有单独的历史备份，无法安全推断已经被清零的原进度；历史最高恶堕也不等于历史锁链进度。
